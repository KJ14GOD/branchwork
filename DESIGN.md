# Design

## Product feeling

Novus must feel: calm, soft, precise, slightly cute, premium, human, quietly technical, comfortable during long sessions, trustworthy, purposeful.

It must not feel: cyberpunk, neon, theatrical, like an admin template, like a generic IDE clone, like a generic AI dashboard, like a terminal multiplexer with decoration, like every component came from a separate prompt.

The resolving rule — every screen is checked against it: **density in the content, softness in the container, personality in the words.**

And the standing correction, because it has had to be given more than once: **quiet, plain, and few.** What a serious engineering tool would ship — flat dark ground, one weight of edge, generous space, text doing the work. No glow, no halo, no stacked panels inside one box, no control that announces itself. If a treatment exists to make something *look* designed rather than to make it readable or reachable, it is wrong here. Concretely, and checkable in review: every dialog closes on `Esc` and on a click outside it; every row of buttons is one size; nothing inside a bordered container carries a second border.

- *Structure is technical*: dense rows, tabular numerals, monospace for paths/SHAs/commands, precise 1px separators, keyboard-first affordances.
- *Chrome is soft*: squircle radii on interactive controls, generous outer margins even when rows are dense, warm off-white text, gentle motion.
- *Voice is cute*: microcopy ("Maya has the baton", "Nothing needs you right now"), small identity marks. Cuteness lives in words and proportion — never in ornament, and never on evidence. Diffs, checks, and receipts are the most restrained surfaces in the product.

## Visual references

Observed on public product surfaces as of 2026-08-01 (facts, not endorsements; structural study only — never copy branding, layout pixel-for-pixel, wording, or decorative identity):

- **Conductor** (conductor.build): the workspace as a single legible unit — branch, files, terminal, diff, and PR path hang off one noun; keyboard-addressable movement between work, diff, checks, and PR; a checks tab as one pre-merge gate; archive/history lifecycle hygiene. Re-observed 2026-08-09 for D-100: the Checks tab aggregates git status, PR metadata, CI and status checks, deployments, review comments, and todos as blockers "until intentionally cleared"; the diff viewer carries inline comments, send-to-agent, and GitHub thread resolution; merge is performed from inside the app once green, with archive as the post-merge act. From an owner-supplied capture the same day: the pull request is **its own tab** in the working row (`PR #7108` beside the workspace tabs, with the number and a green Merge in the window's corner); its page leads with title + number, the description, one action row (Merge · Review · Add all comments to chat), then Comments and Checks as the page's two sub-tabs with the pass count on Checks (`✕ 26/27`); every comment card carries its own **Add to chat**. Borrow: legibility, calm density, direct stage-to-stage movement, one aggregated readiness surface, per-comment and all-comments send-to-chat, cloud workspace lifecycle clarity.
- **Factory/Droid** (factory.ai): explicit autonomy levels with risk-classified actions; a clean separation of "what phase am I in" from "what is permitted"; continuity of one session across surfaces. Borrow: explicit permission boundaries, separation of primary workflow from advanced controls, instruction-to-tested-result directness.
- **Hoplite** (hoplite.sh): cloud execution as a normal expectation; thread statuses as a first-class state machine; inline typed approvals in the activity stream; keyboard-driven navigation; immediate previews; per-run cost legibility. Borrow: cloud-as-default posture, compact task-oriented presentation, approvals living in the stream rather than an admin surface.

Novus's own signature is none of these: it is the multiplayer Mission Room — the baton, the direction thread, the evidence ledger, presence as authorship, and the state line (see [Signature elements](#signature-elements)).

## Tokens

Every visual value in the product comes from this section. A literal hex, px shadow, one-off radius, or unlisted type size in component code fails review ([AGENTS.md](AGENTS.md#rules), rule 14).

Two themes exist: **dark is the default and the reference**; light is a token-for-token override selected by preference (Light / Dark / System, persisted, resolved before first paint — D-029). Components never branch on theme; they consume tokens only. The choice lives in two places and no more: the setup room's Theme row, and the block the rail's foot opens after first run (D-103) — never a page. Light values were proven on rendered screens 2026-08-10 — the populated room, the rail, the settings surface, and a relaunch resolving light before first paint (evidence 115–118).

### Color

Dark, restrained system. No decorative gradients, no neon, no glow, no glassmorphism, no large colored panels. Color is semantic or absent.

| `--surface-1` | `#131316` | Primary surfaces |

| `--edge` | `#FFFFFF` at 11% | Default border; 20% hover |

| `--text-2` | `#B6B1A8` | Secondary text (warm gray): metadata and labels only |
| `--text-3` | `#8B867D` | Faint: timestamps, disabled — never the sole carrier of information |
| `--accent` | `#F2EFE9` | Warm ivory: active state and focus. Authority and activity are monochrome light, never a hue (D-028). Pressed: `#D8D4CD` |

Semantic lock: a token may not be used outside its meaning. Sage for "online" fails review exactly like a raw hex does. Anything not covered by a semantic token renders in neutrals.

Light theme overrides (provisional): `--bg #F2F0EC` · `--surface-1 #FAF9F6` · `--surface-2 #FFFFFF` · `--edge` black 10% (16% hover) · `--text-1 #26241F` · `--text-2 #5D594F` · `--text-3 #77726A` · `--accent #26241F` (authority inverts to warm ink; pressed `#3A3833`) · `--ok #4F7A4A` · `--warn #A15F28` · `--danger #A8443A` · `--lane-current #3F5F85` · `--lane-alt #8A5F1E` · hover/selected/pressed: black 4/6/6%. Same contrast obligations as dark.

Interaction states: row/list hover `#FFFFFF` at 6%; selected `#FFFFFF` at 9% (a background highlight only — no accent bar, no outline); pressed `#FFFFFF` at 9%. Disabled controls: label and icon at 40% opacity, no hover response, default cursor.

#### Terminal palette

The one place hues appear outside their semantic tokens, and the exception is narrow and named (D-046): these are a **foreign program's** colours rendered inside the runtime dock, not Novus saying anything about status. A build tool's red error line is that tool's own rendering; stripping it is what made the previous terminal unreadable. Every value is muted and warm so a log reads as part of the product rather than a neon window cut into it, and no other surface may use them.

`--term-bg #17181b` · `--term-fg` = `--text-1` · `--term-cursor` = `--accent` · `--term-cursor-text` = `--term-bg` · `--term-selection` white 16% · `--term-black #3A3B40` · `--term-red #C97B6F` · `--term-green #8FAE8B` · `--term-yellow #D9A47E` · `--term-blue #7F9CC0` · `--term-magenta #9C8DB8` · `--term-cyan #7FADA8` · `--term-white #CDC9C2`, and the eight bright variants one step lighter. Light theme inverts them token for token, darkening each hue to keep its contrast. The emulator reads these from the CSS variables, so no colour is ever written in component code and a theme change moves the terminal with everything else.

### Typography

- UI family: **Inter** (fallback: system-ui). Mono: **JetBrains Mono** — paths, SHAs, diff content, commands, check names.
- Complete scale (size/line-height, weight). No other sizes exist.

| Step | Use |
| --- | --- |
| 11/16, 500, tracking +0.02em | Micro labels, uppercase section labels |
| 12/18, 400 | Metadata, timestamps |
| 13/20, 400 | Dense rows (mission list, activity, checks) |
| 14/22, 400 | Body, composer text, a direction someone wrote |
| 15/25, 400 | **Harness speech** — what the agent said back. One step above body and the only text at `--text-1` inside a turn, because it is the answer to the question the room exists to ask (D-065) |
| 16/24, 600 | Section headings |
| 20/28, 600 | Surface titles |
| 28/34, 650 | Mission title — one per room, nothing competes with it |

- Weights available: 400, 500, 600, 650. Nothing bolder.
- Tabular numerals wherever numbers align (counts, durations, line numbers).
- Hierarchy floor: every screen uses ≥3 distinct steps. Secondary/muted text is limited to metadata and labels; any sentence a user must act on is `--text-1`.

### Spacing, grid, shell

- Spacing scale (px): 4, 8, 12, 16, 24, 32, 48, 64. No other values.
- Grid: 8px base; rows in dense lists are 32–36px tall; touch/pointer targets ≥32px.
- Shell: top bar 48px, **borderless** — it separates from content by height and spacing alone, never a hairline; navigation rail 240px (Missions surface); Mission Room sidebar 280–320px max; content max-width unconstrained in the Room, 720px for prose-like content (receipts, empty states); outer page margins 24–32px.
- The app shell never scrolls; see [Overflow](#overflow).

### Radii

6px — inputs, rows, small controls, **buttons** (buttons are squarish, never pill-adjacent — D-029). In the rail, **headings are full-bleed and sharp; mission rows are inset chips** (D-078): a mission's highlight is a slightly smaller, 6px-rounded row set in from the rail's edges, while the project heading above it never takes a wash at all. Never a floating capsule with a shadow, and never an accent bar · 10px — contained cards · 14px — dialogs, drawers, the composer · full — identity marks only. Squircle corner smoothing where the platform allows; plain border-radius with the same values where it does not. Radii come only from this list.

### Elevation

- Level 0: none (default; separation by spacing and 1px edges).
- Level 1: `0 1px 2px rgb(0 0 0 / 0.30)` — sticky bars, popovers.
- Level 2: `0 8px 24px rgb(0 0 0 / 0.35)` — dialogs, drawers.
- No colored shadows, no text-shadow, no blur >24px.
- Layers (z-order), lowest to highest: content · sticky bars · popovers and menus · dialogs and drawers · toasts.

### Focus

A **1px** `--accent` ring at 2px offset, on `:focus-visible` only — never removed. A text field is the exception and shows focus on **its own edge** rather than wearing a second one: a ring around a box that already has a border is the border drawn twice, and at 2px it reads as a white slab stuck to whatever you touched (D-076). Focus is the accent's home turf: always visible, always the same, never loud.

**Focus handed back is not focus taken** (D-106). When a dialog closes, the keyboard returns to whatever opened it — but the ring does not, because nobody navigated there: closing with `Esc` is a key press, so the browser calls the restored focus keyboard navigation and rings a control the person never aimed at, which on a hover-only control at the rail's edge is a white box around a `+`. The element keeps the focus and wears no mark until the **next key press**, which restores the ring in place. This is the only suppression of the ring in the product, it is never applied to focus a person moved themselves, and it never blurs anything to achieve it.

### Motion

- Durations: 120ms (hover/press), 180ms (reveal/collapse), 240ms (overlays, the baton handoff). Easing: `cubic-bezier(0.3, 0.7, 0.3, 1)`.
- Motion only on state change. No entrance animations on initial render, no parallax, nothing animates unprompted. Exactly one element in the product may loop: the working indicator while an agent runs (`--motion-breath`: 1500ms opacity cycle — the only looping duration).
- Respect `prefers-reduced-motion`: all motion drops to opacity-only.

### Icons

One approved set (stroke style, 1.5px stroke, 16px default). No icon without adjacent text, except inside an IconButton with a tooltip. No emoji in chrome, states, or buttons — emoji appear only inside user-authored text.

### Identity marks

- Humans: circular mark, 20px (inline) or 24px (headers), 1px edge, wearing **the person's own GitHub picture** — everyone here signed in with GitHub, so the face is already theirs and initials on `--surface-2` are the fallback when there is no picture to show (D-105, reversing "no photos in V0"). The mark's size, shape and edge never change with it; a photo fills the circle and is cropped by it, and it is the only image the product renders as identity. No pile of them anywhere ([Signature elements](#signature-elements), 4).
- Agents/harnesses: rounded-square mark, same sizes, harness glyph, always paired with the harness name in text. Agents are visually distinct from humans at a glance (circle = person, square = machine) and never rendered as characters or mascots.

### Status semantics

Status is **stated in words**, never as a pill and never by color alone (D-047). Diff arithmetic is the one place a number carries `--ok` and `--danger` as *text*: `+3` and `−0` already say which way they go, so the colour agrees with a sign rather than replacing it, and it is the same pair the diff body uses so one change reads identically in the trace and in the panel (D-065). "Running", "timed out", "exited 2", "no one holds the baton" — the sentence is the signal. There is no status dot: a small coloured circle beside text carries less than the text does, and thirty of them scattered across a screen make the machinery the first thing the eye finds on a surface whose subject is a mission. Where a state deserves emphasis it takes weight (500) or a semantic text color within its meaning, never a decorative mark. The working indicator (`--motion-breath`) remains, on the active execution row only.

## Signature elements

Five elements make a screen recognizably Novus. They are the only permitted uses of their respective treatments.

1. **The baton.** Control is *named*, in the same words everywhere it appears: "You have the baton", "Maya has the baton", "No one holds the baton" (D-047). It was a filled `--accent` squircle beside the name, and on a rendered screen that mark was the loudest thing in the window while saying nothing the sentence beside it did not. The phrase is the signature; the answer to "who is in control?" is always that sentence, in that wording, product-wide.
2. **The direction thread.** A submitted direction renders with a left-edge `--accent` line connecting author → direction → the activity it produced. Lifecycle (queued, applied, superseded, rejected) renders as states of that one thread — position and line treatment — not as badges. Everything an execution produced hangs off the direction that caused it, in one trace: the author's circular mark and their words, then the harness's rounded-square mark once for a run of consecutive harness speech, then tool activity collapsed into compact milestones or one disclosure, then changes, then verification, then the outcome. Technical setup collapses into a single subordinate row (`Workspace ready · main @ f88c40df`). An individual protocol event is never centred alone in the canvas — a feed of centred grey fragments is the failure this element exists to prevent.
3. **The evidence ledger.** Verification is a fixed two-column ledger (check name · outcome) in mono, `--ok` only after a check passed, environment attribution beneath. The identical ledger component appears in Mission Room, Review, and Receipt — "verified" always looks exactly the same.
4. **Presence as authorship.** Participants appear where they acted: small identity marks inline on directions, reviews, handoffs, and stops. There is no floating avatar pile; the participant list in the evidence panel's Overview is the only aggregate view (D-066).
5. **The state line.** One persistent single-line strip under the mission title: current state + next action ("Running — Claude Code is editing auth middleware · Pause"). The state name is emphasized by weight (500) in `--text-1`, never by color — the header contains no colored text; it is the answer to "what is happening and what happens next?"

## Information architecture

Project-first (D-032). The window's subject is parallel agent work, never code files. Invitations, permissions, technical logs, environment configuration, and advanced settings live in bounded overlays or contextual inspectors.

1. **Projects sidebar** — the persistent left rail (240px): the user's repositories (GitHub and local), each disclosing its **missions** when the row is pressed anywhere along its length — and this is the only place missions are listed (D-055) — the name is the control, not only the arrow beside it, and the arrow additionally discloses without moving the room; nouns and counts only. **The rail is also the tree** (D-084): under the **active** mission's row — and only the active one — it nests one row per approach (7px identity dot, name), the selected approach's **sessions** one level deeper (title in words, and each background row's own state word — `· needs you` in `--warn`, `· working` and `· queued` quietly in `--text-3`, an idle row saying nothing at all — D-094), and a **Compare** row at the mission level once two approaches exist, reading `Compare · decision recorded` when a decision stands. Rows are navigation — clicking one puts the room on it — the wash sits on the deepest selected row only, and a quiet hover/focus `+` labelled `New session in {approach}` sits on the new session's deepest visible parent — the selected approach's row where approach rows render, the active mission's own row where its one lane is invisible by design — the same convention as the project row's `+` (a parent's `+` creates its child). A mission with one approach and one session grows no tree at all. Plus **Archived** at the foot with a count, present only when something has been filed away and opening a dialog rather than a list in the rail — putting a mission away and taking it back out must not be equally easy, or archival is just a second list (D-063) — a restrained `+` on each repository row — revealed on hover *and* on keyboard focus, labelled `New mission in {repository}`, and never selecting or collapsing the row it sits on (D-061, D-077) — Add project (GitHub picker or local folder), and Join with invitation. A project row is a **disclosure and nothing more** (D-077): click opens its list, click again closes it, and the room never moves — landing somewhere is what clicking a mission does. The heading reads as one: the project name carries weight and `--text-1` over its quieter missions, and it never takes the selected wash, which belongs to the mission row alone. An **attention view** at the rail's top surfaces Needs-you items across projects — the old Missions queue, demoted to a lens. **Home is the board** (D-120): choosing Home shows every active mission grouped by the list projection's own class — **Needs you | Running | Waiting | Decided | Complete**, in that order, because what needs a person is the reason Home was opened and finished work reads last (D-121) — with the open tabs kept in the strip; Home is a glance, never a purge. Columns are fixed-width, side by side, scrolling sideways in their own container with each column owning its vertical scroll; there is **no dragging and no rank** — a card moves columns because reality changed. A card is the second sanctioned contained-card use (after first-run setup): the goal at row weight, the repository and relative time in the meta step, one colored line saying where the state is (`--warn` for attention with the lane named only once siblings exist and the chat's title in quotes; quiet for running and decided), churn as the diff's own text arithmetic (`{n} files +a −d` — `--ok`/`--danger` as text, the sanctioned pair), and quiet facts (checks passed at current heads, approach count past one, the baton where it is one fact). A card's **one action is its click**: open the mission at the thing that is asking — the attention's lane and conversation, the running chat, or Compare for a decided mission with siblings — never a verb that starts, stops, or approves anything. An empty column says so in one left-aligned quiet line ("Nothing needs you right now."); the board renders only once a mission exists at all.
2. **Open missions** — a strip above the **room**, starting at the room's own left edge and never running over the rail, carrying the **working set**: only the missions this person has open (D-061, restored by D-086 after D-085's per-lane tabs read as two missions). A mission is open at most once; which approach its tab is reading is the tab's own state, and the approach tabs live one level below, in the room's strip. Not a second list — a project with nine missions and none open shows nothing here. A tab is the mission's name, its project's name, and a close. `+` at the end opens a draft. The rail is its own full-height column beside it: tabs belong to the pane they switch, and a strip spanning the window would claim to switch the rail too (at narrow widths the rail is an overlay and takes no column, so the strip legitimately spans). It scrolls sideways when it overflows; the shell never does, and the selected tab is always scrolled into view.
3. **Project room** — the center: **the selected mission, and nothing that repeats the rail** (D-055). A mission is chosen in the rail or in the strip above; the room is that mission's room and says so once, in its title. The strip across the *room* belongs to **open files**: absent entirely while none is open, and when one is, the room takes the first tab as the way back to itself — labelled **Mission**, not the goal again, because the strip above and the rail beside already name it (D-061). Multiple workstreams inside a mission, when they exist, are rows in the rail's tree (D-084) **and** colour-dotted tabs on the room's own strip (D-086) — never tabs in the window's mission strip — the tree carrying the structure and the sessions, the strip carrying the quick switch beside the open files, each lane keeping the same room anatomy when selected: the state line, the direction trace, and a persistent composer carrying harness/model selection; Changes and Verification one keystroke away, never the default canvas. Inside a lane, parallel **Sessions** share its workspace and nest one level deeper in the same tree — one conversation on the canvas at a time, every other surface still the lane's own (D-083, D-084). The room's own strip is the mission's **working row** (D-086, D-087): one colour-dotted tab per approach once the mission holds more than one — switched in place, and landing on the approach's **own page**: its one conversation while it has one, its **overview** once it holds several — the intent (or that it is the work the mission started with), one quiet line of its own facts, and its sessions as clickable links, each opening that conversation as a tab (D-089) — then one tab per **open session** — from any approach, in the person's own order — dragging a tab reorders it live, browser-style, the tabs moving while the hand moves and the release needing no aim (D-090) — each leading with its approach's identity dot so blue and amber conversations sit tellably side by side, and staying open when the lane changes — the row holds **exactly what the person opened**, so switching approaches adds, removes, and swaps nothing (choosing a foreign lane's tab moves the room there, exactly as a file tab does — D-088, D-089); the tab is the conversation glyph and the first-words title, a background one wearing its chat's state word (`· needs you` in `--warn`; `· working`, `· queued` quietly — D-094), a close on **every** tab — the approach tab is the way back, so nothing needs to be permanent — then the Compare surface as a closable sibling tab while it is open, then the **pull request's own tab** once a person opens it — `PR #{n}` with its quiet state word, from the rail's `PR #{n} · {state}` row or the receipt's own control, never by itself (D-100, D-089) — then every open file; side by side, one canvas showing at a time, so opening one thing never silently eats another. The single-approach mission keeps the plain *Mission* back-tab instead — while anything else is open, session tabs included — landing on the mission's own page the same way (D-089). A file tab is a path in **one lane's worktree**, captured when it was opened: in a mission with competing approaches each tab leads with its lane's identity dot, the same path open from two worktrees is two tabs, choosing a tab puts the room in that tab's lane, so the dot and the bytes on screen can never disagree, and file tabs drag to reorder exactly as session tabs do — files among files, live (D-090). Approaches and sessions are never tabs in the *window's* strip — up there, one mission is one tab. The trace and the composer share **one content axis**: the same measure and the same left edge, so the room reads as one column rather than two systems. **Creation is a question, not a place** (D-077, D-078): `+` on a repository row, the strip's `+`, and `⌘T` open one Conductor-shaped dialog — the project's name across the top, one large borderless prompt that is the body, and the **real composer's foot** (model chip, effort chip, send control) as the Create row, so the choice made there persists exactly as the room's does. Enter with words creates the mission (goal derives from them) and starts the first turn; Enter with nothing, `Esc`, or a click outside does nothing at all — no draft, no tab, no row. No goal/criteria form ever gates starting work (D-032).
4. **Review** — behavioral result summary; the diff; the evidence ledger; build/diagnostic state; comments; open concerns; PR readiness.

The room keeps Novus's identity inside Conductor-adjacent patterns: state line, evidence ledger, attribution, and (later) the baton are what the tabs contain — not a bare chatbot, and never a file tree as the main event.

## Layout

- Each surface declares one **primary region** occupying ≥55% of width. Sidebars ≤320px. No two regions may have equal visual weight.
- The Mission Room's evidence inspector **docks to the right edge** as a toggleable column, not an overlay (D-039): ≤420px and ≤40% of width, so the room keeps its majority. It is closed by default, opened and closed by the same control, and never traps focus — a docked region is beside the work, not over it. Below 900px it takes the surface, as a full-screen view.
- Machinery is subordinate: model names, repo refs, workspace ids render at the 11–12px steps in `--text-2/3`, inside inspectors — never in the mission header. The mission, not the machinery, is the room's subject.
- Navigation rails contain nouns and counts only. Explanatory prose lives in tooltips or empty states, two sentences maximum.

### Density

Dense where content is (lists, activity, diff: 32–36px rows, 13/20 type); relaxed where chrome is (24–32px outer margins, 16–24px section gaps). Density never comes from shrinking type below the scale, and softness never comes from inflating rows.

### Overflow

The app shell never scrolls. Every surface declares which region owns overflow; only ScrollArea primitives scroll. Wide content (diff, ledger, tables) scrolls horizontally inside its own container. Content may never extend below the viewport unmanaged.

### Responsive

- One layout system for the desktop app's resizable window (the same client later ships in the browser). ≥1200px: full shell. 900–1200px: sidebar collapses to an overlay. <900px: single-column room — state line, activity, composer; Changes and Verification become full-screen views. Nothing hides that answers the eight room questions ([PRODUCT.md](PRODUCT.md#multiplayer-behavior)); things reflow, they do not vanish.

### Accessibility

- Text contrast ≥4.5:1 for every text token on every surface it may appear on, including `--text-3` (`#918C84` ≈4.6:1 on `--surface-2`, higher on darker surfaces); `--text-3` additionally stays restricted to timestamps and disabled labels and is never the sole carrier of information. Token changes must re-verify these ratios. Status never conveyed by color alone (dot + text always); full keyboard operability; visible focus everywhere; `prefers-reduced-motion` honored; all interactive elements labeled for assistive tech; live-region announcements for state-line changes, control transfers, and approval requests.

### Keyboard

- Global: `⌘K` command palette (actions scoped by capability), `⌘1/2/3` surfaces, `⌘J` next needs-you item, `⌘,` the theme block at the rail's foot — the platform's own settings chord (D-103).
- Projects: `⌘T` new **mission** in the selected project — the same ask-dialog as the repository row's `+` (D-077) — and `⌘1–9` its missions in rail order. Shipped, and stated here because a binding that exists and is undocumented is a binding nobody uses.
- Room: `⌘Enter` submit direction, `⌘.` pause/resume, `⌘⇧S` stop (confirms), `G` then `C`/`V`/`A` jump to Changes/Verification/Activity, `R` request control, `O` offer control (controller only).
- Lists: arrow navigation, `Enter` open, `E` archive from Completed.
- Every dialog: `Esc` closes, focus is trapped and restored.

## Primitives

These are the only primitives. Feature components compose primitives; they never invent local styling, and no component may add an arbitrary color, radius, shadow, gradient, type size, or spacing value.

`Button` (primary/secondary/text/danger) · `IconButton` · `TextButton` · `Input` · `Textarea` · `Select` · `Menu` · `Tooltip` · `Popover` · `Dialog` · `Drawer` · `Tabs` · `IdentityMark` · `Row` · `Section` · `Separator` · `ScrollArea` · `Composer` · `EvidenceItem` · `DiffRow` · `CheckRow`

Composition rules:

- Primary Button: `--accent` background, `--bg` text — a light control on a dark product, never a colored one. Secondary: `--surface-1` with a 1px edge. Text buttons: `--text-2`, lifting to `--text-1` on hover.
- **Every button variant is the same size**: one height (32px minimum, which is also the pointer-target floor) and one padding, whatever its weight. Buttons sharing a row are the same object in different emphases, and a primary standing taller than the secondary beside it reads as two unrelated controls (D-076).
- Exactly one primary Button visible per surface state. Everything else renders secondary, text, or icon.
- Maximum one border level per region: a bordered container never contains another bordered container. Nesting is expressed by spacing and type, never a second border. Section separation defaults to whitespace or a 1px Separator, not a card.
- Maximum one pill-shaped element per row; pills are interactive filters/toggles only. Status is words (see [Status semantics](#status-semantics)); new badge variants require a change to this document.
- New primitives require a DECISIONS.md entry.

## Component behavior

- **Composer.** One bordered field containing the input and its controls: the textarea sits on the box's own surface (no nested border), and a foot row inside the box carries the model chip (harness glyph + model name), the effort chip, the **permissions chip**, and the send control at the right edge. Model and effort selectors may only offer values the harness actually accepts — each maps to a real flag; a capability that does not exist renders disabled with a plain "arrives later" note, never as a live option. Selection persists across sessions and is recorded on the execution's start event, so a receipt can say which model and effort produced the work.
  - *The permissions chip* (D-115) wears the lane's permission profile — `Permissions · {label}`, the label in `--warn` text only for Don't ask — where directing happens, because how supervised a lane is belongs under the fingers that direct it. Unlike its neighbours it is a lane fact, not a per-send choice. The chip opens the **profile picker** (D-117, the owner's shape, named from Codex's approval menu after D-116's slider was tried and set aside): one `--type-meta` question as the head — "How should Claude Code's actions be approved?" — then one row per profile in autonomy order, Plan to Don't ask, each row a quiet stroke glyph, the name at `--type-row` 500, and one short `--type-meta` line of meaning beneath it — a fragment, never a paragraph, because a mode nobody can explain is a mode nobody chose. The current row carries a check at its end; the **Don't ask row wears `--warn` whole** — glyph, name, meaning, and check as one word — so its danger is read before its name is; and one quiet foot line explains the deliberate absence: there is no bypass — the harness always asks; a profile changes who answers, from the next turn. The chip renders for anyone who can read the composer and disables with the capability named for anyone without `policy.set` (the Permission-denied pattern); the Don't ask stop additionally disables where the role is short of Mission Admin. Choosing Don't ask opens a confirmation on the dialog's own axis (D-076, the D-100 anatomy): the profile named with its consequence beneath, two quiet fact groups — what is approved without a person, and what stays the server's whatever the profile — and the danger Button on the right reading "Set Don't ask, accepting this"; the sentence confirmed is recorded verbatim. Every other stop sets on one click, its meaning already on the line. Persistent in the room, proportionate: idle height one input row (≤56px), grows with content to 40% of viewport maximum, and **resets to one row after submission**. It sits on the same content axis and measure as the direction trace above it — never its own wider slab. It states its behavior in placeholder microcopy per state (see matrix). Non-controllers' composer submits to the queue and says so. In a multi-workstream room it submits to the focused workstream and names it in the placeholder. It is never a large blank canvas.
- **Evidence inspector.** All files, Overview, Changes, Verification, and Output are the sections of one right-docked panel. It is a **full-height column against the window's right edge**, owning that corner of the shell: its own top row carries the section triggers and the control that hides it — no identity row, because who holds the baton is the room's sentence said once beneath the mission title, and the participants are Overview's list (D-066). A single IconButton in the top bar shows it again — the one control that is always reachable regardless of which section was last read, carrying a tooltip and a label because it has no adjacent text. The room header keeps the state line and the baton; the section triggers live only in the panel, so the room is never a second navigation. Each section's trigger is also a toggle: pressing the section already showing closes the panel, and the active trigger reads as pressed. Sections: **All files**, **Overview** (repository, mission branch, base ref and abbreviated SHA, branch status, runner and environment, participants and roles — all the machinery the header may not carry — and **Project skills**, D-118: the published manifest as quiet rows, each the skill's name in mono, the lane's standing answer in words — nothing while off, `enabled` quietly, `changed since enabled` and `no longer in the project` in `--warn` — the frontmatter's own description beneath, and one text action at the row's end, Enable or Disable, disabled with `skills.set` named for anyone without it; a foot sentence states once that a skill grants nothing, and a project that declares none puts nothing here; **MCP servers**, D-119, follow on the same row anatomy — the description is the server's observable behavior, `runs {command}` or `connects to {host}`, the action gated on `mcp.set` with the Mission Admin tier named, and the foot sentence stating that a server is new tool surface whose tools still ask a person under every profile short of Don't ask), **Changes**, **Verification**, **Evidence** (D-122, below), **Output**. *All files* and *Output* read the machine holding the checkout, so they appear only there — a participant elsewhere is not shown a section that can only refuse (D-042, D-050).

- **Output** (D-050). The full local output of the project's own processes, with a three-way switch for setup, the app, and checks. A switch in front of a terminal is in the way, because that request is unambiguous; a switch here is the shape the panel already has, because inspecting is what it is for. Each run names its command in mono and how it ended — **timed out**, **cancelled**, **could not start**, or **exited {code}** — and a process that has ended stays readable. Where more than one run of a kind exists they list, newest first. This is the detailed local log, and it never leaves the machine: the trace shows the milestone, the ledger shows the bounded attributed result that supports a claim (D-045).

- **All files** (D-048). The workspace's own files, folders first, disclosing in place so a reader sees where a file sits rather than walking a path a level at a time. `.git` and dependency directories are never listed. A row carries a small tinted badge of the file's extension — a fact about the file, in the same way the terminal's palette is a fact about a foreign program, and the second and last place hues appear outside their semantic tokens. Selecting a file opens it over the room's canvas.

- **A file over the canvas** (D-048). Opening a file replaces the direction trace for as long as the reader wants it, and closing returns the trace exactly as it was — a file is read at full measure or not at all, and a column of source in a third of the window is the generic-IDE shape the product refuses. The composer stays: reading a file is not a reason to stop being able to direct. The header carries the path in mono, its size, and one action set — for markdown, **Preview** and **Edit**; for everything else, its source. A file that is not text says so, and one too large to show says how large it is and where to open it instead. Preview renders markdown to elements and never to markup built from the file's own content; links show their destination rather than navigating. A section renders only once its data exists; an empty fictional destination is prohibited pattern 11. Repository revision belongs to Overview, secondary to the mission.
- **Diff.** Per-file DiffRows: path (mono), +/− counts (tabular), state. Expanded: unified diff, mono 13/20, additions/deletions tinted at 12% background opacity of `--ok`/`--danger` — the only place those tokens appear as backgrounds. Inline comments attach to lines and appear in Review.
- **Verification.** The evidence ledger (signature element 3). Each row carries its **origin** — observed from the agent, run by a named person, run by Novus at the checkpoint ("Run by Novus at the checkpoint", in the same quiet meta style with no colour and no badge), or reported by CI — because collapsing those into one green row is the fabrication the ledger exists to prevent. A row also carries the abbreviated revision it proves — and, while the lane holds more than one conversation, whose checkpoint that revision was (`proved {sha} · "{title}"'s checkpoint`, D-096): attribution by trigger, never by content, because the worktree a check exercised holds every chat's work so far. When the workspace has moved past the revision the row dims and says so rather than continuing to read as current. Raw command output lives one reveal away and never in the trace. Checks never render as pills; a pending check is `--text-3`, running `--accent` dot, passed `--ok`, failed `--danger` with its output one reveal away. Environment attribution ("reported by cloud workspace wsp_…") always visible — evidence is a claim with an origin ([PRODUCT.md](PRODUCT.md#principles) P3).
- **Mission-list row.** 36px: mission title (13/20, `--text-1`), repo ref (12/18 `--text-2`), controller's IdentityMark, needs-you reason in `--warn` text when applicable, relative time (`--text-3`, tabular). No progress bars, no thumbnails.
- **Run.** One compact `Run ▾` control in the room's workspace controls, beside the Terminal and Evidence toggles — never a second navigation and never a toolbar. Its menu lists only what the project declared: the setup command, each named run command with the default first, and each named verification command — read from what the machine hosting the workspace **published** (D-043), so a participant who is not at that machine sees the same list and may invoke the ones their capabilities allow. While a run command is alive the control collapses to the running command's name with Stop, and Open preview appears only when a live process reported an address; it opens the **Preview surface** in the room (D-098, below), whose validation is the loopback-only bridge's own (D-045). A command a participant cannot invoke renders disabled with the capability named. Suggestions Novus inferred come from a local reading of the project, appear only on the hosting machine, are marked as suggestions, and open the setup dialog rather than running.
- **The Preview surface** (D-098). The running app inside the room: a closable sibling tab on the working row exactly as Compare is, opened only from Open preview — never by itself — and lane-captured like a file tab, because the preview shows one lane's app; choosing the tab moves the room to its lane. Its head is the approved origin in mono, the **process's own state word** in the runtime vocabulary — *starting*, *running*, *running, not answering*, *stopped* — and four text actions: **Capture screenshot** and **Start recording** (D-122, D-123, both gated on `artifact.capture` through the denied-not-hidden pattern; a successful capture answers with one quiet meta confirmation, "Captured at `{short sha}` — in Evidence" or "Recording saved — in Evidence", that clears itself), Reload, and Open in browser (the D-045 external bridge). While a recording runs the two capture actions are replaced by the recording's own state: **`Recording · {m:ss}`** in `--warn` with the elapsed time ticking in tabular numerals, a secondary **Stop recording**, and a text **Cancel** — and the preview *tab* carries `· recording` in the warn tone so the state survives a canvas switch, exactly as a session tab carries its chat's word (D-094). A recording that is being preserved reads `Saving recording…` with both controls disabled. One quiet meta line under the head is the standing capture warning, verbatim from the one shared sentence: captured pixels are the application's own output and may contain sensitive data — Novus redacts known secrets from text, never from pixels. A capture or recording refusal renders as the surface's own inline note in the refusal's words. Recordings carry no audio, stop themselves at the stated bound, and end as *interrupted* — named in the artifact — when the app or the preview goes down mid-recording; cancelling leaves nothing anywhere. The body is a reserved rectangle the embedded page fills; a page loading is never presented as the application being ready, because readiness stays the declared signal's answer (D-045). Every state that is not a page on screen is words in the rectangle with **only the correct next action**: a page that did not answer offers Reload (or nothing while the app is still starting, where waiting is the action), a crashed page offers Reload, a stopped app says how it ended in the process's own words and offers running it again — or reopening, once a live process reports an address again. Closing the tab closes a window onto the app and never the app; stopping lives on Run, and the surface never grows a Stop, an address bar, or any navigation chrome — it is a view of one running application, not a browser. The embedded page paints above the room's own DOM, so whenever anything of the room's would overlay its rectangle — a dialog, a menu, the narrow-width dock — the page yields and the rectangle waits empty until clear.
- **Evidence** (D-122). The panel's visual-evidence section: restrained thumbnail rows, newest first — a 48×32 thumbnail (an empty `--surface-2` rectangle where none is verified), the generated label at the row step, and one meta line (capture time · abbreviated revision, with `+ uncommitted changes` when the tree was dirty · a recording's length). Thumbnails are evidence, not decoration: no gallery, no cards, no oversized media. State is words on the label — nothing for plain available evidence, `uploading` quietly, `interrupted` in `--warn`, `failed` in `--danger` — never a pill and never color alone. The empty state is one sentence — "No visual evidence yet. Open the running app's preview and capture a screenshot there." — followed by the standing pixels warning. Selecting a row opens the artifact on the room's canvas; the Mission Room never becomes a media manager, and no internal object key or signed URL renders anywhere.
- **An artifact over the canvas** (D-122). Selecting evidence opens the artifact's own view where the worker's view opens (D-108): the canvas, never a tab, `Esc` or **Back to chat** returning the reader where they left. Head: the label at the section step, the state word where one applies, the meta line, and two text actions — **Copy provenance** and Back to chat. Body: the full image, or the recording in a native `<video>` player with its poster frame — bordered at the card radius, never larger than its container. Beneath it, always, the honest claim verbatim: a screenshot proves what the preview displayed at this revision and time, and does not prove the application is correct (the recording variant says the same of its span) — an image is never presented as a verification outcome. Then the provenance ledger as quiet label/value meta rows: captured when and by whom (a person by name, or "Requested by the agent, approved in the room"), the full revision with dirtiness stated, the process and validated origin in mono, readiness in the declared-signal's words, the reporting runner, the SHA-256 digest, the byte size, an interruption or failure reason where one exists, and where the artifact is currently evidence ("Not attached to anything yet." until it is). A pending or failed artifact opens to its own words instead of media; bytes ride the `novus-artifact:` protocol and nothing else.
- **Set up workspace.** A bounded dialog, not a wizard: detected project type, the proposed setup command, proposed run commands, proposed verification commands, the **filenames** of required local files (never their contents), the **variable names** this project calls secret, and where the configuration will be written — the shared project file or this machine only. One primary action. Nothing runs until it is pressed. Local files are copied only after explicit consent, only when Git confirms they are ignored, and the dialog states plainly that Novus reads their names, not their values.
  - *Values only this machine has* (D-044): one row per declared secret name, with the words **supplied on this machine** or **not supplied** — never characters, and never a mask, because a mask is still a length. Supply, Replace, and Forget are the only actions; nothing reads a value back, because no verb can. A value held for a name the project no longer declares says so and offers Forget. On a machine whose operating system has no credential storage the section says that plainly and offers nothing, and on any other machine it says a value is supplied where the workspace is hosted.

- **Invitation.** Inviting lives in the inspector's Overview, with the participants it changes, gated on `mission.invite`. One row: the role being granted and the action. The issued token is shown **exactly once**, selectable and copyable, stated plainly as single-use and expiring — the server stores only its hash and cannot show it again. Unredeemed invitations list with a revoke action; redeemed ones collapse to a count. The receiving side is a single-question dialog reached from the rail, because someone who has been invited has no project, no mission, and nothing else to click.
- **Participants.** A list in the evidence panel's Overview, one row per person: identity mark, name, role — the panel's header carries no copy of it (D-066), and who holds the baton is the room's own sentence in words, never a mark beside a name (D-047). The signed-in person's own identity and sign-out sit at the foot of the projects rail, not in the top bar — the top-right corner belongs to the mission, not to the account. The account corner also carries the one theme control (D-103): a quiet glyph beside sign-out that **is the resolved theme** — a crescent while the product is dark, a sun while it is light, System wearing whichever it resolves to — opening a small block anchored right there (`⌘,` reaches it too, revealing the rail first if it was put away): three icon segments and no words — sun, crescent, display, each labelled for assistive tech, the active one washed `--selected` — hugging their content one plane above the rail, closed by a click outside or `Esc` (D-104). Never a dialog and never a page — a reversal of D-102's dialog on the owner's direction. Connection state is on the wire (D-091) and renders on the row ([PRODUCT.md](PRODUCT.md#presence-and-connection)): a disconnected participant dims to 40% with the state said in words beside the role — "reconnecting" or "offline", never a dot — and never disappears.
- **Control request.** An inline row in the activity feed (not a toast, not a modal): requester's mark, "requests control", Offer/Decline for the controller, quiet `--warn` dot while open.
- **Handoff.** The offer renders as a card-level row addressed to the recipient with Accept/Decline; on accept, "waiting for a safe boundary" appears in the state line; at the boundary the baton animates to the recipient (240ms) and an attributed event lands in the feed.
- **Turns.** No rule drawn beside a turn. Grouping is the indent of speech under its speaker and the space between blocks; a line down the page repeats what the spacing already says and competes with the only mark that means anything, which is the speaker's (D-065). Within a turn the reading order is deliberate: the agent's words are the largest text and the only `--text-1` inside the turn, the direction that prompted them sits at `--text-2`, and everything *about* the turn — who spoke, model and effort, the permission profile it ran under when not the default (D-115, the word alone: `· Accept edits`), what it cost, technical activity, the checkpoint line — is `--type-meta` at `--text-3`. Speech is content; the rest is apparatus. A profile-decided answer renders as a technical-activity row (`allowed by policy · Write`, with the same bounded summary a card would carry and the profile in parentheses), never as a card, because nothing waited; a profile *change* is a room-level sentence like the baton's ("{name} set permissions to {label}"), with Don't ask's sentence carrying its meaning. What a turn was handed states itself the same way (D-118, D-119): `Project skills carried: {names}` and `MCP servers carried: {names}` as quiet apparatus rows when any were, and each entry the turn could not carry as its own row in the `--warn` tone — `… not carried — "{name}": {reason}` — because a standing enablement that no longer names real bytes is news a person acts on; a turn with nothing enabled says nothing.
  - *What the turn cost* joins the machinery line beside the model and effort — tokens in and out, the harness's own cost figure, and how long it took, as plain text with tabular numerals (D-071). A figure the harness did not report is absent rather than zero, and none of it is ever a tile, a meter, or a chart (prohibited pattern 16).
  - *The harness's own workers.* Where a harness forwards what its internal subagents said, that activity is grouped by the ids the stream itself stated (D-107) and presented as **the turn's own worker rows** (D-108, on the owner's sight of the first build): the milestone anatomy, like CHECKPOINT — a `workers` label, then one quiet line per worker carrying its purpose (the Task call's own description, the only identity the harness stated), the last thing it did in mono, and its state in a word — `working` quietly only while the turn is live, `done` quietly, `failed` as the word in `--danger`, and *nothing* when the turn settled without the end arriving, because an unstated end is not a state. This is the terminal's shape, graphically: one line per subagent, **Enter steps in, Esc steps out**. Stepping in opens the worker's own view on the canvas — the same facts at reading size: activity timeline, the files its own calls named, its handed-back report or failure, and *Back to chat* — returning to the conversation at the position the reader left. Decision identifiers never appear in this surface's copy. A worker never takes the speech position, never appears in the rail, a tab strip, or the baton, and never gets a lane, a mark, a breathing indicator, or a cost of its own: the reply that leads is the harness's, and a subagent is the harness's business ([PRODUCT.md](PRODUCT.md#the-harness-boundary)). Activity whose parent id joins to no recorded spawn stays what it always was — indented grouped activity inside the technical disclosure, no identity claimed.
- **Side columns are draggable.** The rail and the evidence panel are both columns a developer lives in — project names run past 240px and a diff's readable width is a property of the code, not of a number chosen once. Each has a hairline handle that takes no layout width, is keyboard-operable (arrows step, Home resets), double-clicks back to its default, and remembers its width on that machine. Bounded so neither can be dragged to nothing or made to swallow the room (D-065).
- **Workstreams.** One workstream: no workstream chrome at all — the room is the workstream, and nothing above it lists anything (D-055). Multiple (D-080's routing, D-084's presentation): the rail's tree carries **one row per lane** — the 7px identity dot (`--lane-current` / `--lane-alt`) and the lane's name — with the mission-level **Compare** row beneath them; the canvas is always the selected lane's own room, with one quiet line under the title saying which lane it is ("Alternative · isolated workspace · forked at `{sha}`"). Every lane keeps its own trace, files, terminal, checks, evidence, and composer, and the composer's foot names its target ("Directing Alternative") — a direction always carries the lane on screen, never silently the first one. The mission's row keeps its "2 approaches" count for when the tree is folded away with its project. There are no lane tabs and no **Approaches ▾** switcher: the tree is the one answer to "what lanes are there", in creation order, with no row highlighted as better — here or anywhere.
  - *Starting one.* **Try another approach** is a plain secondary control in the room's own controls, present only once there is a result to fork from — a shared checkpoint on the lane being read (D-079). While the mission has one lane and a reviewable result, one quiet helper sentence sits beside it: "Start from this shared checkpoint and compare another solution." It opens a bounded dialog whose single required field is the **intent**, asked as "What should this approach try differently?" with "Describe the solution you want to compare." as the placeholder. The dialog states the mission's goal, the exact shared checkpoint ("Starts from shared checkpoint `{sha}`. Changes made only in {lane} stay there."), that this starts an isolated workspace leaving the current lane unchanged — with the project's saved setup and the local files already approved for this repository carrying over automatically (D-081) — and a hint that approaches solve the same mission in meaningfully different ways — unrelated work belongs in a new mission. If no shared checkpoint exists the dialog says so and the primary action stays disabled; it never guesses a revision. The primary action reads **Start approach**. Nothing about it is a wizard and nothing about it suggests parallelism is the normal thing to do.
  - *Naming.* The lane a mission starts with is named **Current work**; a fork defaults to **Alternative**, then **Alternative 2**. Names identify lanes, never quality.
- **Sessions.** One session: no session chrome at all — the room is the conversation, exactly as before (D-083). Multiple (D-084): the rail's tree carries one row per session of the **selected** approach, nested one level under it — the title is the session's own first words, truncated with an ellipsis; an unwritten one reads **New session** in `--text-3`; every background row carries its chat's own state word (D-094) — `· needs you` in `--warn`, `· working` and `· queued · {n}` quietly in `--text-3`, an idle row saying nothing, the selected row saying nothing because its state is the room's state line — and the needs-you words climb to the approach's row while that approach is not the one being read. Rows are the navigation and the inventory at once: creation order, no row marked better, the wash on the selected one. A session row in the tree opens that conversation as a tab on the working row — every row, the approach's first included: opening is always the person's own act, and nothing opens or swaps by itself (D-087, D-089). Closing the tab puts it away and never touches the conversation, and closing the one being read falls back to the approach's landing. The approach's row and tab land on its **overview** once it holds several conversations: the intent (or that it is the work the mission started with), one `--text-3` line of its own facts — conversations, the lane's permission profile in words (`{label} permissions`, D-115 — the fact a Viewer with no composer still reads), files changed, checks passed once any ran, and what the lane has spent so far: its turns, its harness time, and the harness's own cost figure, each absent rather than zero when unreported (D-113, carried as claims per D-071; counts are text in a row, never a tile) — then, when two chats' checkpoints have changed the same file, one warn-toned sentence naming the chats and the path with any further overlaps counted quietly (D-094; evidence from checkpoints only, never a prediction), and one glyph-led link per session: first-words title, the chat's state word (`· needs you` in `--warn`, others quiet), its ownership, footprint and evidence at the row's end in the meta style — `owns {patterns}` where a scope stands (D-097), `{n} files`, `{p}/{n} checks at its checkpoints` (D-096: checks attributed by the checkpoint they ran at, never "its tests" — the worktree a check exercised holds every chat's work), `last heard {time}` while working — hover underlining the name; clicking one opens it (D-089). Beside each row, for the baton holder only, a quiet **Scope** word opens the one scope dialog (D-097): a mono textarea of patterns one per line, prefilled for an unscoped chat from the directories its own turns touched, a plain sentence stating the contract — writes inside stop asking, writes outside are refused, provably separate chats run at once, Bash still asks — and Set scope / Clear scope / Cancel. The composer's queue-or-alongside question (D-095) simply does not appear where scopes make the answer moot: a disjoint chat's send dispatches, in parallel, with nothing to choose. A scoped turn's checkpoint line carries its drift in the warn tone — `{n} files outside its scope, uncommitted` — because what a turn's shell touched beyond its own ground is the one thing its evidence must not absorb silently. A lane with one conversation lands straight in it — no page between a person and their only conversation. A new session starts from the selected approach row's quiet hover `+` (`New session in {approach}`), opening an **empty conversation**: the canvas says "The first direction starts this session.", the composer is the ask, typing creates and titles it, and leaving creates nothing anywhere (D-077 one level down) — while it is being asked, the tree shows it as an untitled row. The canvas is the selected session's own conversation and composer; the state line stays the **lane's** and names the working session ("Running — Claude Code is working in {title}") once more than one exists; a pending approval renders whichever session is selected — the question blocks the lane's one workspace — attributed with `asked in {title}`. The composer's foot names its whole target ("Directing {lane} · {title}"), and a direction sent while a sibling session's turn runs asks the baton holder first (D-095): one inline sentence naming the running chat, then **Queue** (the default a second Enter takes) and **Run alongside · read-only** — never a dialog, because the question is about the words already in the box; editing them or `Esc` withdraws it, and a question gone moot (the turn ended while it was being asked) submits the ordinary way rather than swallowing the click. Anyone without the baton keeps today's behavior: the direction queues with the confirmation in the server's own words, naming the session it waits for. A chat answering alongside reads as its own room: `· read-only` on its turn's machinery line, and the state line — which stays the write turn's story — gains `· answering read-only` with the read turn's own quiet Stop while that chat is on screen. Files, changes, checks, terminal, and output stay the lane's: sessions share the workspace, and the surfaces say so by not forking.
- **The Decision Room.** Where two or more approaches exist, one surface compares them and nothing else does. Its header reads **Compare approaches** with the shared checkpoint stated beneath it ("Shared checkpoint · `{sha}`") when every fork genuinely started from one revision — with mixed origins the header claims nothing and each column's own Revision row carries the truth. With three or more approaches the columns do not multiply: a selectable row of lane chips picks **the pair being compared**, one click swapping one column. It is a column per approach on one horizontal axis, each column carrying, in fixed order and identical shape: the approach's **name and intent**, its state, its changed files with the same `+`/`−` arithmetic the trace uses, the checks that ran with their outcomes and origins, **what was not verified** stated as plainly as what was, the human interventions it took (directions, approvals answered, stops), the time and cost it reported, and the risks a person has written down. Columns are the same width and the same order every time; there is no highlight, no ordering by quality, no total, no score, and no recommended column — a comparison that ranked would be a recommendation, and PRODUCT.md's non-goals forbid one. A row with nothing in it says *not verified* or *none recorded*, never a blank or a dash: the absence is the finding.
  - *Contested changes.* One control per file that both approaches touched — **Inspect contested changes** — opens the two diffs of that path side by side. Nothing is merged, nothing is auto-resolved, and neither side is marked correct.
  - *The four things a person can do* sit together at the foot, one primary among them: **Choose this approach** (primary, per column), **Request revision**, **Keep exploring**, and — after choosing — **Record decision**. Choosing opens the decision surface rather than committing anything: a decision is not a click.
  - *Recording one* asks for a rationale in the person's own words and will not proceed without it, offers the accepted risks as free text, and shows two things before the confirm: **the evidence this decides on** — the lane's changes, its checks, and the exact revision the decision will pin — and the outstanding checks it is about to record as unresolved, so nobody records a decision without seeing both what they are accepting and what was never verified. The mission's state line then says a decision was recorded and that nothing has been published, because those are two facts.
- **The receipt of a decision.** Same components as the room, at the receipt's 720px measure: what was chosen, by whom, when, at which revision; the rationale verbatim; accepted risks; unresolved checks as the evidence ledger's own rows; the approaches that were not chosen, kept as evidence with their own intents and results; and the publication half (D-099). While nothing has been opened: the **prepared pull request** — title, body, base and head branch, rendered read-only with a copy action — and, where a host could receive one, the publish controls: the branch's remote standing in words (*never been pushed*, *pushing*, *pushed at the decided revision*, or the failure's own reason), **Push branch**, and **Create draft PR**, enabled only once the host serves exactly the decided revision, with the reason on the disabled control. Once a request exists, its **page** replaces the projection: the approach it publishes, head → base with the pushed revision in mono, the changed-file and check arithmetic, mergeability as the host's own sentence (`--warn` on a conflict only), review status with its read-only ingested threads, **Request review** (typed GitHub logins) and **Mark ready for review** (drafts only), a screenshots-and-videos section that states plainly nothing is attached while the artifact store is unbuilt, the verbatim snapshot that was sent, and **Open on GitHub**. Every control is `pr.manage`, rendered through the gated pattern. There is no merge control, and the page carries the sentence that says where merging happens instead — the absence is the design.
- **Cloud workspace lifecycle.** Rendered in the state line + an inspector: provisioning (progress as text, no spinner theater), ready, suspended, failed (provider error verbatim, Retry provisions new). Workspace machinery never occupies the canvas.
- **Repository continuity.** The workspace inspector shows location, mission branch, abbreviated base SHA, abbreviated workspace SHA, and one synchronization state: Up to date, Update available, Syncing, or Sync failed. These are compact label/value rows, not badges or a permanent status dashboard. Update available offers Inspect commits as the primary action; after inspection, Sync workspace is capability-gated and states that it waits for a safe boundary. Uncommitted files on another machine are never implied to be present. Local-mirror controls do not render in V0.
- **Add project.** A dialog, never a rail popover. Fixed title `Add project`; a source switch (`GitHub` / `On this Mac`); the GitHub identity or installation context stated plainly; a search field focused on open; one dedicated ScrollArea for results with the header, search, and contextual actions fixed outside it — they never scroll away at any window size. Repository rows are 36–40px: repository name primary, owner and default branch secondary at the 12px step, a source glyph from the sanctioned set. No raw provider identifier and no absolute local path is ever the primary text of a row. Keyboard: Up/Down, Home/End, Page Up/Down, Enter to open, Escape to close, focus trapped and restored to the trigger, the focused row scrolled into view. States, each with its own plain sentence: loading, empty, no results, offline, GitHub App not installed, insufficient repository permission, local folder cancelled, invalid git repository, local repository unavailable on this machine.
- **The terminal dock.** A bottom dock in the room, closed by default, sharing the room's width and never replacing the trace; below the single-column threshold it becomes a dedicated full-room view. **The dock is the terminal** (D-049): it carries sessions and nothing else, and it opens straight into a live shell. It had a four-way switch — Terminal, Setup, App, Checks — which put a page about terminals in front of the one surface where the request is unambiguous; setup, the app, and a check each have their own surface already (below). Detailed local output is bounded, redacted, and kept on the machine that produced it, and is read in the evidence panel's *Output* section (D-050); the split with the trace and the ledger is unchanged (D-045).
  - *One plane.* From the tab row to the last line of output the dock is a single surface on `--term-bg`, with one edge between it and the room. Chrome in a different colour above a shell reads as a window inside a window. Beneath the one row of controls the screen fills the dock edge to edge with a single left gutter: the dock is short by design, and framing it in padding spends its height on margin.
  - *Sessions.* Showing the dock opens a session and gives it the keyboard — showing the terminal is the request, so the screen is there at once and the session lands in it; there is never a button that opens a terminal inside a terminal. A tab is a glyph, its name, and a close (D-047). A name is **derived, never typed**: the repository's own short name and the tab's number — `branchwork 1`, `branchwork 2` for `KJ14GOD/branchwork`, `robinhood-agentic 1` for a folder of that name — so the row says which project these shells are in without a label anyone has to maintain, and nothing in the interface renames one. `+` makes the next number and selects and focuses it, switching tabs shows that session exactly as it was rather than restarting it, and closing the last one opens a fresh shell. The dock closes from the toggle that opened it and carries no Hide of its own — a second control that only does what the toggle does is a word on screen doing no work. Rendering is a real emulator, so colour, cursor addressing, alternate screens, and interactive programs work (D-046). Scrollback is bounded and local. It is available only on the machine hosting the workspace, and the room says why in words rather than hiding the control: controlling the mission is not unrestricted access to the host machine (D-042).
  - *Where setup, the app, and checks live.* Setup is the setup dialog, opened by the mission state's own action and by `Run ▾ → Set up workspace`. The app is `Run ▾`, which collapses to the running command with Stop and Open preview. A check's result is the evidence panel's ledger, attributed and bound to the revision it proved, and a row whose answer is out of date — failed, errored, or proving a revision the worktree has moved past — carries **Run again** (D-057). A row that passed and still proves the current revision does not: an action offered everywhere stops meaning anything, and a green current check is not asking a question. Running one again adds a record; it never replaces the one that failed. The **detailed local output** of those three — each naming the command in mono, its state, and, when it ended, its exit code or the reason it stopped by name (**timed out**, **cancelled**, **could not start**, **exited {code}**) — is captured and kept, and is read in the evidence panel's **Output** section (D-050) — the surface this paragraph once left open, and the section above already specifies. "It failed and the output is gone" remains the state that view prevents, and it is prevented at the machine, not by the switch.
  - A run command that declared a readiness signal reads **starting** until that signal answers, **running** once it does, and **running, not answering** if its own deadline passes — the process is not stopped for it unless the project asked (D-045).
- **First-run setup.** The signed-out surface is a setup room, not a login page: no top bar and no hairline — the window's top inset is a full-width drag region and the traffic lights sit over the canvas. Content sits in the upper third, title left; the connection-card row aligns to the right edge of the content column. Title "Set up Novus" at the mission scale, one subtitle sentence, then the card row — the one sanctioned card grid in the product. Each card: official service glyph (monochrome, `currentColor`, from the sanctioned brand-icon set — D-029), name, one-line description, a separator, and a status row. GitHub is interactive (Connect → plain waiting text while the browser leg runs → "✓ Connected as {login}" in `--text-1`). Harness cards report *observed local facts* — CLI detected on this machine, signed-in plan where the CLI's own files state it — as claims about this Mac, never as Novus capability; when nothing is detected they say so plainly. Cloud execution wording stays future-tense until it exists (sole sanctioned mention of unreleased capability, D-028). Below the cards, a Theme row: label and one-line description left, a three-option segmented control (Light / Dark / System) right; the selection applies immediately and persists. Once connected, the surface's single primary action is "Finish setup", bottom-right. Waiting and error states are plain text — no dots, no spinners.
- **Review.** Result summary in prose (what the change does, per the mission's success criteria), then diff, then ledger, then comments/concerns as attributed rows, then PR readiness as a CheckRow list (approvals, checks, conflicts). One primary action: Request revisions or Accept result (capability-gated).
- **Receipt.** A single scrollable document (720px measure): goal, participants and roles, timeline of applied directions and control transfers, changes summary, the evidence ledger's final state, review outcomes, PR reference, and an explicit "remaining uncertain" section. Same components as the room — a receipt is the room, frozen.

## Transient states

- **Loading.** Quiet placeholders: `--surface-1` blocks in final layout positions, no shimmer animation. Structure appears first, content fills in.
- **Empty.** Left-aligned, one sentence + one action, no illustration. Missions empty: "No missions yet. Start one when you have work worth doing together." Never a decision UI over nothing: comparison views require two artifacts, "needs decision" requires a real decision.
- **Errors.** Inline at the failure site, `--danger` text + recovery action. Full-surface errors only when the surface cannot render at all: route load failure, authentication failure, or a missing resource.
- **Offline/reconnecting.** A single-line notice bar under the top bar — `--surface-1` background with `--warn` text; there are no filled color bars anywhere in the product: "Reconnecting — the room is current as of 14:32." No modal, no blur; stale content stays readable and read-only.
- **Permission denied.** The action stays visible but disabled, with a tooltip naming the capability and who has it ("Only the controller can pause. Maya has the baton."). Denial is informative, never mysterious; hidden actions are reserved for Viewer-irrelevant chrome.
- **Destructive confirmations.** Dialog with consequence stated in one sentence, the danger Button on the right, and typed confirmation only for irreversible org-level actions. Stop-execution confirms with one click; force-interrupt states what will be interrupted.
- **Toasts.** Only for outcomes with no visible surface result; one at a time; 4s; never for errors that have an inline home; never stacked.

## State presentation

Keyed verbatim to [PRODUCT.md](PRODUCT.md#the-mission-state-model). Fields per state: message (the state line), primary action (the one primary Button — states of unattended progress deliberately have none), secondary, canvas, sidebar, composer, evidence, participants, color, recovery. Fields not stated inherit from the preceding primary state; the sidebar defaults to participants and the project's missions; overlay states change only the fields they name and never replace the primary state's layout.

**New mission** — "Set up the workspace to begin." · Primary: Provision workspace · Secondary: Edit mission · Canvas: goal + success criteria · Sidebar: participants, repo ref · Composer: disabled, "Available once the workspace is ready" · Evidence: none · Participants: Overview lists all participants with connection state · Color: neutral · Recovery: n/a.

**Workspace needs setup** — "Workspace needs setup — configure it before running." · Primary: Set up workspace · Secondary: none · Canvas: the trace, unchanged · Composer: enabled, because direction is not blocked on a runnable project · Evidence: none · Color: `--warn` dot · Recovery: the setup surface names what is missing.

**Provisioning workspace** — "Setting up workspace — {step}." · Primary: none (in progress) · Secondary: Cancel · Canvas: goal + provisioning step as text · Sidebar: unchanged · Composer: disabled, same copy · Evidence: none · Color: `--accent` dot · Recovery: on failure → Workspace failed.

**Workspace failed** — "Workspace setup failed." · Primary: Retry (new workspace) · Secondary: View provider error · Canvas: error verbatim, mono · Sidebar: unchanged · Composer: disabled · Evidence: none · Color: `--danger` · Recovery: retry provisions new; error preserved in history.

**Ready for instruction** — "Ready — tell {harness} what to change." · Primary: composer submit · Secondary: Invite teammate · Canvas: goal + success criteria · Sidebar: participants, workspace ready · Composer: focused, "Direct {harness}…" · Evidence: none yet · Color: neutral, `--accent` focus · Recovery: n/a.

**Agent starting** — "Starting — preparing the mission worktree." · Primary: none · Secondary: Stop · Canvas: activity feed begins · Composer: enabled (queues) · Evidence: none · Color: `--accent` · Recovery: start failure → inline error + Retry.

**Agent running** — "Running — {current activity summary}." · Primary: Pause · Secondary: Stop · Canvas: activity feed streaming; direction thread visible · Sidebar: workstreams, files touched count · Composer: controller "Steer {harness}…" / others "Add direction to the queue…" · Evidence: checks appear as they run · Participants: working indicator on the execution row · Color: `--accent` · Recovery: disconnects → Runner offline overlay.

**Agent stopping** — "Stopping — {harness} was asked to stop." · Primary: none · Secondary: **none while the stop still has a claim to work** — the action that belongs here has been taken, and a Stop still on screen after a Stop invites a second press and says nothing about the first. Once the stop has gone unanswered for a minute (or the machine has gone quiet), the line appends *the stop has gone unanswered* and offers **Force interrupt** to those who hold `force_interrupt` (D-111) — the escalation, never the first resort; the server refuses it in words while the grace holds · Canvas: activity feed as it was, no longer growing · Composer: enabled (queues) · Evidence: current · Color: `--accent` · Recovery: Force interrupt after the grace; a runner that dies while stopping is ended by the sweep as *interrupted*.

**Needs direction** — "{Harness} is waiting for direction." · Primary: composer submit · Secondary: Stop · Canvas: feed + the harness's question highlighted at bottom · Composer: focused · Evidence: current · Color: `--warn` dot · Recovery: n/a. Missions surface: Needs you.

**Needs approval** — "{Harness} asks to {action}." The line names the act and stops; what is being asked for is on the card, in the thread that raised it, because "may I run this" is only answerable by someone reading what came before it (D-062). What reaches this state at all is the lane's permission profile's residue (D-115): under the default profile everything, under Accept edits and Auto what the policy left to a person, under Don't ask nothing — and a profile-decided act renders as apparatus in the thread, never as a card. · Primary: **Approve once** (lease holder only) · Secondary: Deny · Canvas: the request rendered plainly — the tool in `--warn` mono and one bounded, redacted sentence, never the tool's raw input · Composer: enabled · Evidence: current · Participants: everyone else sees the question, is told who holds the baton and can answer it, and is offered Request control where their role allows · Color: `--warn` on the tool, and nowhere else — nothing has gone wrong, something is being asked · Recovery: deny returns to running with the denial as context, not as a failure. The scope is stated beside the buttons ("This one act only — nothing is remembered"), because *Approve* alone reads like a policy — and it stays true under every profile: a card's answer never becomes one. Needs you (controller).

**App running** *(overlay)* — state line appends "{name} running on :{port}"; the Run control offers Stop and, where a live process reported one, Open preview, which opens the Preview surface in the room (D-098). Independent of the harness: it neither blocks direction nor ends with a turn. Where the project declared a readiness signal the overlay reads "{name} starting on :{port}" until that signal answers, and says so plainly if its deadline passes — a process existing is not a claim that an application is serving (D-045).

**Verification stale** *(overlay)* — the ledger's rows dim to `--text-3` and read "proved {short SHA}, since changed"; the primary action becomes Re-run verification. A stale row is never counted as passing in the state line.

**Direction queued** *(overlay)* — while the lane is idle, the state line is the queue's: "Waiting for {controller} — {n} direction queued". While the harness is working, the backlog is a quiet suffix on the working line instead — "· {n} directions queued" — because a controller's own queued work was otherwise invisible at line level (D-112). The thread shows queued position and its author; composer confirms "Queued — applies at the next safe point"; author may cancel from the thread.

**Control requested** *(overlay)* — inline request row (see Component behavior); `--warn` dot on the participant stack; controller's Needs you.

**Handoff offered** *(overlay)* — offer row addressed to recipient, Accept/Decline primary for them; expiry countdown as text.

**Handoff waiting for boundary** *(overlay)* — state line appends "Handing control to {name} at the next safe point"; if the timeout passes: stall notice + Force interrupt (controller / Mission Admin) with consequence stated.

**Paused** — "Paused by {name}." · Primary: Resume (controller) · Secondary: Stop · Canvas: feed frozen at pause point, marked · Composer: enabled (queues) · Evidence: current · Color: `--warn` dot, calm · Recovery: n/a.

**Verification running** — "Verifying — {n} checks running." · Primary: none · Secondary: Stop checks · Canvas: feed + ledger with running rows · Evidence: ledger prominent · Color: `--accent` · Recovery: check-runner failure marks affected checks failed with output.

**Verification failed** — "{n} checks failed." · Primary: Review failures · Secondary: Re-run checks · Canvas: ledger with failures expanded first · Composer: enabled — revision direction is the expected next act · Color: `--danger` on failed rows only, chrome stays calm · Recovery: direction → new execution turn. Needs you.

**Work completed but unverified** — "Work finished — {n} files changed, nothing verified." · Primary: Run verification · Secondary: Review changes anyway · Canvas: changes + empty ledger stating plainly what did not run · Color: `--warn` · Recovery: verification or explicit acceptance-with-uncertainty (recorded in receipt).

**Ready for review** — "Ready for review — {n} checks passed." · Primary: Open review · Secondary: Request changes via direction · Canvas: result summary + changes + green ledger · Evidence: full · Color: `--ok` on verified rows only · Recovery: n/a. Needs you (reviewers).

**Revision requested** — "{Name} requested revisions." · Primary: composer submit (revision direction, pre-linked to the request) · Secondary: View request · Canvas: request + affected evidence · Color: `--warn` · Recovery: new execution turn.

**Decision recorded** — "{Name} chose {approach} — not published yet", and once publication has resolved, the sentence names how instead: "— published as PR #{n}, merged by {who} on GitHub" or "— PR #{n} was closed on GitHub without merging" (D-099); "not published yet" after a merge would be a lie. · Primary: **none** — the sentence is the state, and the decision is read and revisited on the Compare surface, reached from the rail's `Compare · decision recorded` row (D-084); no button repeats what that row already offers · Canvas: the selected lane's own room; the decision receipt lives on Compare · Composer: enabled, because a decision is not the end of the mission · Evidence: the chosen workstream's ledger, with unresolved rows shown as unresolved · Color: neutral; `--ok` only inside the ledger and only for checks that actually passed · Recovery: a later decision supersedes this one and both stay in the record. The line never says "done": choosing and applying are different, and the second has not happened.

**Pull request open** — "Pull request open — PR #{n} is a draft — merging happens on GitHub" (or "Pull request ready — PR #{n} awaits review", with its open-comment count and "conflicts with its base" when the host says so, D-099). · Primary: **none** — the sentence is the state, and the request is read and stewarded on its own page in the decision receipt, reached from the rail's Compare row (the D-084 rule) · Canvas: the selected lane's own room; the request's **own tab** carries its page — headline and description, one action row, then Comments, Checks with its pass count, and Changes as the page's segments (the Conductor anatomy, owner-directed) — while the receipt keeps only the headline and the way in · Color: neutral; `--warn` on the conflict sentence only · Recovery: a merged or closed request returns the mission to *Decision recorded*, whose sentence names how publication ended ("published as PR #{n}, merged by {who}" — never "not published yet" after a merge). There is no merge control anywhere, and the page says why in words.

**Completed** — "Completed {date}. Receipt saved." · Primary: **none** — the canvas already is the receipt, and a View-receipt button over it would be a control doing no work (D-121) · Canvas: the receipt, rendered from the snapshot stored at close · Composer: hidden · Color: neutral; `--ok` only inside the ledger · Recovery: n/a. Terminal states never resume; every action here is read-only, and the fork control is absent.

**Cancelled** — "Cancelled by {name} {date}." · Primary: **none** — the canvas already is the receipt (D-121) · Canvas: receipt including what was abandoned, the person's own words quoted · Color: neutral, not red — cancellation is an outcome, not a failure · Recovery: n/a. Ending lives in the inspector's Overview: Complete as a plain control whose refusals are the server's own sentences, Cancel behind a confirmation stating the consequence with room for the person's words.

**Execution interrupted** — "Interrupted — {reason}." · Primary: Restart execution (a continuation in the same workstream) · Secondary: View last activity · Canvas: feed ending at a marked interruption point · Composer: enabled — direction queues for the next execution · Evidence: current, honestly partial · Color: `--warn` · Recovery: restart consumes the queue; nothing is lost. Missions surface: Needs you.

**Execution stalled** *(overlay)* — state line appends "no progress reported since {time}". The recovery is Stop, which the line already offers; a stop that then goes unanswered surfaces Force interrupt on the *Stopping* state (D-111), every use logged to the feed. No dot — status is words (D-047).

**Repository sync error** *(overlay)* — a notice row in Changes and the state line names the cause ("GitHub token expired", "branch conflicts with main"); primary for capability holders: View remediation (inspector with the error verbatim, mono); direction still queues; `--danger` on the sync row only, chrome stays calm.

**Reconnecting** *(overlay)* — the notice bar (see Transient states): "Reconnecting — current as of {time}." Room read-only; composer disabled preserving draft; on restore, bar resolves and backfilled events land marked.

**Runner offline** *(overlay)* — state line: "Runner offline — last event received at {time}." Actions requiring the runner disable with tooltips; direction still queues durably; on reconnect, events backfill with a gap marker if any ([ARCHITECTURE.md](ARCHITECTURE.md#runner-plane)).

**Repository update available** *(overlay)* — state line appends "Repository update available — agent is on {short SHA}." Primary in the workspace inspector: Inspect commits · Secondary after inspection: Sync workspace (controller only; waits for a safe boundary) · Composer remains enabled and names the pinned revision in its context tooltip · Color: `--warn` dot on the inspector row only · Recovery: explicit sync succeeds to the reviewed target SHA or moves to Repository sync error. Missions surface does not become Needs you unless the active execution requires the update to proceed.

## Prohibited patterns

Each rule is testable in review; violating any one fails the review.

1. No CSS gradient functions anywhere (AGENTS.md rule 15).
2. No raw color values in component code; tokens only, used within their semantic.
3. No glow: shadows only from the elevation scale; no colored shadows; no text-shadow.
4. No pills for status; max one pill per row, interactive only.
5. No cards in cards; max one border level per region.
6. No screen with fewer than three type-scale steps.
7. No page scrolling: only ScrollArea scrolls; the shell never does.
8. No equal-weight regions; one primary region ≥55% width per surface.
9. No composer taller than one row at idle, anywhere. It grows with content to a 40%-of-viewport ceiling and returns to one row after submission. A composer occupying an empty room is a failed screen, not a prominent one.
10. No prose in navigation rails.
11. No decision or comparison UI over empty content.
12. No machinery (model, repo, workspace ids) in the mission header.
13. No emoji, mascots, sparkles, or cartoon robots anywhere in chrome.
14. No skeleton shimmer, no entrance animations, no unprompted motion; nothing loops but the working indicator.
15. No toast stacking; no toast for anything with an inline home.
16. No numeric stat tiles, donut charts, or dashboard furniture in V0 surfaces; counts are text in rows.
17. No center-aligned marketing-style empty states; no illustrations in empty states.
18. No new primitive, token, or badge variant without a DESIGN.md change and DECISIONS.md entry.
19. No Tailwind-default or library-default palette values leaking through (`blue-500` et al. fail review).
20. No presentation-only privileged actions: anything rendered as available must be server-enforced ([AGENTS.md](AGENTS.md#rules) rule 13).

Review procedure: implementation changes touching UI attach a screenshot; the reviewer checks it against this list and the [composition rules](#primitives). Text rules alone do not catch composition failures.
