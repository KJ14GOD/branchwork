# Architecture

## The three planes

Novus is three planes with three trust levels. The planes are an isolation contract, not a deployment diagram — two planes may share a process in development and must still respect the boundary.

- **Control plane** — the durable collaborative product state: identity, organizations, missions, participants, capabilities, leases, direction, events, receipts, PR state. It is the only party trusted with org-wide state. It stores, relays, and authorizes. It **never executes**: no repository code, no harness binaries, no user-supplied commands, no git operations against customer code. If the control plane ever runs customer code, the isolation story is dead.
- **Runner plane** — repositories, harnesses, commands, tests, and execution. A runner is **semi-trusted at best**: it executes model-generated code, so every runner is treated as potentially compromised from the moment an execution starts. Runners receive only short-lived, mission-scoped credentials and see nothing beyond their mission.
- **Client plane** — the desktop application (and, later, browser delivery of the same client). Untrusted input, period. Clients render from server state and submit commands; they decide nothing privileged.

## Trust and security boundaries

### Secret placement

| Secret | Lives in | Never reaches |
| --- | --- | --- |
| OAuth client secrets | Control-plane secret store | Runners, clients |
| Database credentials, event-store credentials | Control plane | Runners, clients |
| Runner-token signing keys | Control plane | Runners, clients |
| Repo access token (the runner owner's own OAuth token, D-223 — no longer narrowable per repository) | Handed per operation, held by the **runner supervisor** | The harness process's readable environment |
| Harness/provider API credential | Scoped per execution where the harness supports it | Other missions, other orgs |
| Per-project environment secrets | Injected into the workspace encrypted-at-rest, decrypted at provision | Control-plane logs, events, receipts |
| User OAuth access token (D-101: authors the person's own PR comments) | Control plane, on the user row; refreshed at sign-in | Clients, runners, events, receipts |
| Artifact-store credentials and URL-signing secret (D-122) | Control plane | Runners, clients, harness; signed URLs themselves expire in minutes and are never stored, logged, or written into events or receipts |

### The supervisor/harness boundary

The runner supervisor (the Novus runner daemon) holds the connection token and git credentials. The harness runs as a child process in a workspace where credentials are injected **per operation** (git credential-helper / askpass shim), not written to `~/.git-credentials` or exported into environment variables. Rationale: the coding agent can read any file in its sandbox, so anything on disk or in its env is disclosed-by-default. The boundary everyone skips is the one between the supervisor's secrets and the harness's filesystem view; Novus does not skip it.

Harness account credentials on shared cloud workspaces are an explicit policy question: V0 uses org-provisioned harness credentials scoped to the execution, never a participant's personal harness login on a shared machine — participant B must not be able to exfiltrate participant A's token through the agent. Recorded as D-013 in [DECISIONS.md](DECISIONS.md).

An accepted disclosure boundary, stated so it is never a surprise: per-project environment secrets are decrypted *into* the workspace, so anyone whose direction the harness follows can cause them to be read. That is inherent to giving the agent the environment it needs; the protections above are for secrets the agent does not need.

Because those files really are in the worktree, every surface that can carry a file's name or contents out of it asks one policy before it does: checkpoint capture, evidence, and the file browser's list, read, and write. A path that looks like a credential — `.env` and its variants, registry and git credential stores, private keys, service-account files — is refused, with `.env.example` and its spellings exempt because a repository commits one to be read. The refusal is enforced in the Electron main process at the chokepoint all five routes already pass through, so a renderer asking for the path directly is refused rather than merely not offered it; there is no control-plane route and no runner command for reading a file, so a remote participant has no path to one at all. Reported text is masked for machine-local paths and then redacted of values this machine holds, including passwords harvested out of forwarded proxy configuration — the harness transcript included, which until D-052 had only the first half.

Both halves are lists and neither is detection. Path patterns recognise conventional names, not a credential someone put in `notes.txt`; redaction removes literal occurrences of values Novus was explicitly given and cannot see one it was never handed, an encoded form of one it holds, or one split across two delivery chunks. **Novus does not detect arbitrary secrets.** The controls that carry the weight are the ones above, which keep credentials out of the reported path in the first place.

### What each plane may never do

- Control plane: execute anything (above).
- Runner: see other missions' workspaces, the control-plane database, org membership beyond its mission's participant list (display names and ids only), or any long-lived secret.
- Client: originate authority. Every capability check happens server-side ([Authorization](#authorization)); the client's capability list is a rendering hint.

Runner-reported facts are **claims**. Events carry their origin; verification results are recorded as "runner X in environment Y reported…" and presented that way ([PRODUCT.md](PRODUCT.md#principles), principle 3).

## Event model

The event log is the mission's memory and the receipt's source. If a receipt needs data that is not in events, the event schema is incomplete — fix the schema, not the receipt.

**Durable (events):** direction lifecycle, all three control machines, execution lifecycle, workspace lifecycle, repository revision observations and sync attempts/outcomes, harness activity summaries (turn boundaries, tool activity, approval requests), file-change summaries, verification outcomes, review actions, PR state changes, participant joins/role changes, receipt snapshots.

**Ephemeral (never events):** presence, typing, cursor position, live token streams. Full harness transcripts are stored as Artifacts referenced by events, not inlined per-delta into the log. Presence's one stored fact is the participant row's `last_seen_at`, overwritten in place (D-091): it produces no event, enters no receipt, and holds no history — ephemeral in meaning, with exactly one timestamp of storage because a projection needs somewhere to read from.

Every event carries:

```
event_id, org_id, mission_id, workstream_id?, execution_id?,
actor { kind: user | harness | runner | system | external, id },  // never ambiguous; external carries a source (github, ci)
cause { direction_id? , lease_id? , offer_id? },        // what authority it acted under
origin_seq,            // runner-assigned monotonic seq for runner-origin events
schema_version,        // per-event versioning; events are migrated forward, never rewritten
occurred_at, recorded_at
```

Ordering and idempotency: runners assign monotonic per-execution sequence numbers; the control plane persists and dedupes on (`execution_id`, `origin_seq`). Commands to runners carry idempotency keys; a retried command after a partition is applied once. Control-plane-origin events are ordered by a per-mission sequence. Reconnection resumes from the last acknowledged sequence in both directions.

**Client fan-out** (D-149). A client watching a mission holds one server-sent event stream, `GET /missions/:missionId/stream`, and is *told* the mission moved rather than asking on a timer. What crosses is an **address** — mission, sequence, event kind — and never a payload: the watcher re-reads through the same authorized projection every other reader passes, so the stream widens nothing a person may see and the projection stays the single place that decides it. The notification is emitted by Postgres inside the transaction that writes the event, so it is delivered on commit and never on rollback — a watcher is never told to re-read a row it cannot yet see — and a second control-plane process fans out to its own watchers from the same channel. Standing is resolved once at connect; a stream is refused with the same 404 as the mission read, which does not confirm the mission exists. A signal only ever means *re-read*, so a dropped stream costs latency and never truth, and every client keeps a slow re-read of its own beneath it. Runner traffic is unaffected: D-035's polled command transport and D-021's socket destination for the runner's bidirectional channel both stand. **The rail holds one stream for everything else** (D-179): `GET /streams/missions` carries the same addresses for *every mission the watcher participates in*, so background missions stop being learned about by re-reading the whole list — and every mission's detail — on a timer. Fan-out is org-keyed on the bus (the notification carries `orgId`), so a mission created mid-stream speaks from its first event; authorization stays per mission and per event: an address is forwarded only once the watcher's participation in that mission is on record, re-resolved the moment an unknown mission speaks and again on a slow beat so removals take effect, because here the address *is* the payload and an address for a mission you cannot read leaks that it exists. This connection touches no presence and no lease — those are facts about a room being read, not an app being open. The client answers a signal with two bounded reads, each debounced: the named mission's detail, and the list — whose rows carry the board fields the detail path deliberately leaves null — with a 45-second sweep beneath it all as the D-149 floor.

Retention: org-configurable audit retention. Deletion requests are honored by **redaction** — payloads are removed, the event skeleton (id, kind, actor kind, time) remains so receipts stay structurally honest and say "redacted" rather than lying by omission. The receipt-vs-deletion tradeoff is recorded as D-014.

## Runner plane

### Connection model

**The runner always dials out.** Commands down, events up, over a connection the runner opens. Novus-managed cloud runners use the same protocol and direction as local and enterprise runners — no special cases, or there would be two protocols. The control plane never needs inbound access to any runner.

The shipped transport is **authenticated polling** (D-035): the runner asks for its own commands, acknowledges delivery, reports completion, and posts sequenced events. A persistent bidirectional stream (D-021) is the destination and changes the transport, not the semantics — idempotency keys, ordered delivery, per-execution sequence numbers, acknowledgement, and de-duplication are all defined here and carry over unchanged.

**The poll is now told when to happen** (D-154). A runner holds `GET /runner/stream` — server-sent events under its own credential — and receives a bare signal when a command is enqueued for its lane: `event: work`, empty payload, emitted by `pg_notify` inside the enqueueing transaction so it is delivered on commit and never on rollback. The runner then asks `GET /runner/commands` exactly as it does on its timer, so **every guarantee above stays in the queue and none of it enters the transport** — a signal that says only "ask" cannot lose a command. The timer remains as the floor and adapts: fifteen seconds while a stream is live, and the original two seconds without one, so a network that will not carry SSE degrades to the previous behaviour rather than to something worse. One stream per enrolment, because a runner credential is scoped to one workstream and that scoping is what makes the endpoint safe.

**Runner identity** (D-035). A runner registers for one workstream and receives a cryptographically random credential; the control plane stores only its SHA-256 hash, scoped to (organization, mission, workstream, runner), with an expiry and a revocation flag. Runner requests carry it under a `Runner` authentication scheme distinct from user sessions, so a session can never be mistaken for a runner and a runner can never act as a person. Only this credential may write harness-, runner-, execution-, workspace-, or verification-attributed records; the server chooses actor attribution, validates every payload against a closed union of event kinds, and bounds every field. Expired, revoked, wrong-workstream, and wrong-execution credentials are rejected by name.

Runners buffer events locally while disconnected in a bounded outbox: a monotonic per-execution sequence, retry with backoff rather than a hot loop, a flush at clean shutdown, and — on overflow — a **gap marker** event naming the dropped range, so receipts state gaps honestly rather than reading as complete.

A runner also keeps its own **at-most-once** record of the commands it has handled, written before the work starts and again when it ends (D-070). Idempotency keys make a *retried delivery* land once; this makes a *restarted machine* not begin the same work twice. A command the record says this runner began and never finished is acknowledged failed with that reason, and an execution it named is reported `interrupted` — resume-or-restart stays the human choice ([PRODUCT.md](PRODUCT.md#control)).

### Runner protocol (shape, not wire format)

Commands (control plane → runner): `provision_workspace`, `sync_repository`, `checkpoint_workspace`, `start_execution`, `apply_direction`, `pause`, `resume`, `stop`, `force_interrupt`, `run_setup`, `run_command`, `stop_command`, `run_verification`, `respond_approval` (the controller's typed answer to an `approval_required` event), `report_boundary_request` (transfer pending — ack at next safe boundary), `destroy_workspace`. All carry idempotency keys. The three workspace-command kinds additionally carry the **pinned snapshot** of the command being authorized — the exact line, working directory, deadline, and digest the control plane published — and the runner executes that rather than re-reading the repository's configuration, which may have changed since (D-043); a workspace command arriving without one is refused rather than resolved. `stop_command` instead carries the process ids the control plane still records as live under the named command: the runner stops what it is actually running, and reports any named id it is not running as exited — so a "running" row whose real exit report was lost is corrected by the Stop instead of outliving it. `start_execution` and `apply_direction` carry the turn's session, its own resume point (D-083), the chat's scope (D-097), the lane's permission profile (D-115), the lane's enabled skills and MCP servers (D-118, D-119), and the direction's pinned references (D-182 — files by path, checks with their facts snapshotted at submit, said to the harness in a text block before the words), each pinned at dispatch under the same rule: the turn runs what was authorized, not what the rows say by the time it runs. The commands realized so far are `start_execution`, `apply_direction`, `stop_execution`, `respond_approval`, `report_boundary_request`, `run_setup`, `run_command`, `stop_command`, and `run_verification`; there is deliberately **no shell command** in the protocol, so remote interactive access to a local machine is structurally absent rather than merely unauthorized (D-042); the rest are protocol surface with no implementation yet. `sync_repository` carries the expected local and remote SHAs plus the authorizing lease id; `run_verification` executes checks defined in repository-level configuration; mission success criteria may add manual confirmations, recorded as VerificationChecks attributed to the confirming participant.

Events (runner → control plane): workspace lifecycle transitions, the **declared command list and the skill and MCP manifests** whenever the project says something different from what was last published (D-043, D-118, D-119), repository revision observations, checkpoint and sync outcomes, execution lifecycle transitions, harness activity summaries, `harness.usage` (what the harness says a turn cost — see [Harness protocol](#harness-protocol)), `boundary_reached`, `approval_required` (opaque harness payload passed through), `approval.policy` (a permission question the lane's profile answered itself, D-115 — tool, decision, deciding profile, and the same bounded redacted summary a card would carry; recorded-and-nothing-else, because nothing waited), file-change summaries, process start / readiness / exit, verification outcomes, heartbeats, gap markers. A harness activity event may carry the id of the tool call that produced it, which is how a harness's **own** subagent activity is grouped under the turn that spawned it (D-071); such activity never becomes a workstream, a branch, or a controller of its own. Since D-107 the join is complete in both directions: a `harness.tool` event also records the tool call's **own** id, so a worker's tagged events connect to the exact call that spawned them, and the spawning call's tool result — the one lifecycle fact the harness exposes about a worker's end — is recorded as `harness.worker.ended` with the result's own error flag and the worker's handed-back report — for a spawn the CLI runs in the background (D-202), recorded from its `task_notification` rather than from the launch receipt that answers the spawn call at once, and carrying the usage the CLI states for that worker; the runner keeps the CLI's stdin open while any background task is still pending, because the waiting `result` is not the turn's last word and the follow-up turn must still be able to answer a permission prompt. Both are recorded-and-nothing-else: no side effects, no state machine, no worker rows anywhere in the schema — a worker is a projection over these events, or it is nothing. There is no heartbeat *verb*: a runner's liveness is a side effect of the authenticated polling it already does, and the control plane's sweep reads the last-seen time that polling maintains. A *turn's* liveness is its own fact (D-114): the runner emits `execution.heartbeat` every few minutes while the harness process is alive, recorded-and-nothing-else — the stall watch never counts a pulse as progress, because a wedged process breathes too; what the pulse buys is the difference between "alive, saying nothing" and "nobody is there".

The protocol is versioned from day one; version negotiation happens at connection time.

### Execution providers and workspace lifecycle

Novus does not build a microVM platform first. An **execution provider** is an adapter that can provision isolated workspaces on some substrate (Novus-managed cloud sandbox in V0; a customer VM, a third-party sandbox service, or an enterprise runner later). The provider interface owns only lifecycle; the control plane owns the state machine:

`requested → provisioning → ready → active → suspended → destroyed`, with `failed` reachable from any non-terminal state and carrying the provider's error verbatim. Retry after `failed` provisions a **new** workspace; there is no silent reuse. Providers report transitions; they never invent states.

Workspace contents at `ready`: repository checkout on a mission branch, dependency setup per repo configuration, scoped credentials via the supervisor boundary, harness installed. Network policy: egress restricted to an org-configurable allowlist (package registries, the repo host, the harness's model endpoint) — default-deny is the goal, default-logged is the V0 floor (D-015).

**Release** (D-155). Closing a mission enqueues one `release_workspace` command per lane, inside the closing transaction, so a mission that ended is one whose machines have been told and a machine that is offline does the work when it returns. The machine stops that lane's processes and terminals, removes its staged attachments unconditionally (the artifact store holds them, so the disk copy is a cache), and then removes the worktree — **unless anything else is uncommitted**, in which case the workspace is kept and the reason and file count are reported as `workspace.released` with outcome `kept`. The **mission branch is never removed**: it carries every checkpoint, the receipt names it, and a pull request may point at it. Archival does not release anything — filing a record away is not finishing with the work (D-121). Enrolment ends with the checkout, and the lane's command stream closes with it.

### Workspace configuration, environments, and processes

Configuration is two TOML files under `.novus/` in the repository (D-040): `settings.toml`, committed and non-secret, and `settings.local.toml`, gitignored and machine-local, layered over it key by key. The control plane never parses either; they describe how to build and run code, which is the runner's business and the repository's history. Novus may *propose* commands from package manifests, lockfiles, Makefile, justfile, Taskfile, development documentation, `.env.example` variants, and `.worktreeinclude` — a proposal is never executed without an explicit human confirmation that writes it to one of the two files.

**Local files.** A worktree holds tracked files only, so a project needing an ignored file is unprepared until a human supplies it. Preparation is explicit and bounded: only paths Git confirms are ignored, only after consent, never dependency directories or build output, rejecting any path that escapes the source repository or the destination worktree and any symlink resolving outside it, preserving safe permissions, and never entering a checkpoint, diff, event, transcript, screenshot, receipt, or log. The renderer and the control plane see filenames; contents stay on the machine. A person may also **type an ignored file in** (D-226) — the `.env` no machine has yet: written by the main process only after Git confirms the path is ignored (a tracked path refuses in words — it would land in the next diff as nobody's change), always 0600, the path remembered in the machine-local settings, removable under the same ignored-only rule, contents crossing one way and never read back. Secret *names* may likewise be declared from the dialog into `settings.local.toml` (D-226); values still travel only through the D-044 supply path. Tracked files stay out of the person's reach in Novus: changing source is the mission's own attributed work, or the person's editor on their own checkout.

**Three environments** (D-041), constructed explicitly, none inheriting the parent wholesale: the harness process gets a minimal base plus its own credential path and no project secrets; project commands get a minimal base, Novus workspace variables, shared settings, machine-local settings, and only explicitly selected secrets, and never the harness credential; an interactive terminal gets the project environment plus the user's own shell profile. Novus variables are `NOVUS_WORKSPACE_ID`, `NOVUS_MISSION_BRANCH`, `NOVUS_PORT`, `NOVUS_PORT_RANGE_START`, `NOVUS_PORT_RANGE_END`; `NOVUS_WORKSPACE_DIR` is set for the terminal only, because an absolute path is a fact about a laptop.

**Process supervision** lives in the runner, never the renderer. Setup commands are finite; run commands are long-lived; verification commands are finite and cancellable; terminals are PTY-backed. Every process is spawned into its own process group so stop, restart, and application shutdown reach the whole tree. Output is bounded and redacted before it can become shared evidence, and kept locally afterwards so a process that ended is still inspectable. Ports are allocated as a persisted per-workstream range so two workstreams on one host never collide. Nothing runs in the user's original checkout. After a relaunch the runner reports what is actually true — a recorded process is not presented as running unless the operating system still has it, and a process identifier recorded before the machine last booted is never signalled, because by then it may belong to somebody else.

**Deadlines** are the project's, stated in its configuration and bounded by validation (D-043): a default for setup and for verification, an optional per-command override, and a documented maximum. A finite command that passes its deadline is terminated with its whole process tree and reported as **timed out**, which is a different ending from a non-zero exit, a signal, a cancellation, and a failure to start. A run command has no deadline; neither does a coding-agent execution, which does not use this supervisor at all (D-034).

**Readiness** is declared, never inferred (D-045). A run command may name an `http` health URL or a `port` to probe, with its own deadline and an explicit `stopOnFailure`. Until the signal answers the process is `starting`; when it answers it is `running`; when the deadline passes it is `unreachable` and still running. Novus stops a process for a failed health check only when the project asked it to.

**Secret values** are supplied on the machine that has them, through local IPC that the control plane has no route to (D-044). Novus refuses to hold a value shorter than the length it can reliably remove from command output, and refuses outright on a machine whose operating system offers no credential encryption — a plaintext secret on disk is worse than an unprepared workspace, and unprepared is a state the product knows how to say. Nothing reads a value back: the renderer learns a name and whether it is supplied.

**Local previews** open through a narrow bridge: `http`/`https` only, a literal loopback hostname, no credentials in the authority, no control characters, and only an address a live process of that workstream actually reported. When *matching* a request against what was reported, the loopback spellings — `localhost`, `127.0.0.1`, `[::1]` — are one machine written three ways (D-157): a process that reported one has honestly reported them all, while scheme and port still have to agree because a port is an application. The spelling equivalence widens matching only, never what counts as loopback, and it applies identically to the embedded preview's admission and its navigation containment. The URL is rebuilt from validated components and handed to the operating system's external-browser API. No shell command is involved (D-045).

**The embedded preview** (D-098, rebuilt in D-163) is the same gate with a stricter tail: the in-window surface is an in-DOM `webview` element — the page keeps its own isolated renderer process while compositing in the room's own stacking order, so the room's menus and dialogs sit above it as ordinary DOM and no native-overlay choreography exists. Authority stays in the main process end to end: `preview.open` approves only an address a **live** run process of the workstream reports right now — an address whose process ended is refused, where the external bridge accepts anything the workstream ever reported — and `will-attach-webview` refuses any element whose address or partition is not that standing approval, replacing whatever attributes the renderer wrote with the locked-down set: sandboxed, no preload, no Node, no `window.novus`, an isolated in-memory session per workstream, unthrottled in the background so a page off the canvas keeps living and a capture photographs its live render. On adoption the page's top frame may be browsed by the person to any credential-free `http`/`https` address (D-224, reversing the original origin confinement) — `will-navigate`, `will-redirect`, and the window-open handler admit the web and refuse the platform: `file:`, `javascript:`, `about:`, smuggled credentials, and control characters never load, `window.open` and `target="_blank"` open no second window (the element allows the guest to *ask* — `allowpopups`, without which the request is blocked before the handler and such links click dead — and the handler denies every window, loading a navigable address in place) — with every OS permission denied without a dialog and downloads refused. The approved origin remains the surface's identity even so: the agent's drive verbs and evidence capture act only while the page is on it (a capture of wherever the person browsed, attributed to the lane's process, would be a provenance lie), and the address bar's typing is resolved in the main process, a missing scheme meaning `https` and never a search. The surface holds up to eight **tabs** (D-225), each its own guest process under the same clamp and the lane's one in-memory partition: a tab exists only through `preview.newTab` — registered in the main process first, the attach gate admitting an element only for a registered tab's exact address — the active tab is what the bar, the drive verbs, and capture act on, an inactive tab stays painted at opacity 0 (the D-170 rule per tab), and the process ending takes every tab down as `stopped`. When the reporting process ends, the surface says how it ended; the page loading never claims readiness, which stays the declared signal's answer. A person may also open their own artifact with the OS default application (D-165): the main process fetches the bytes over the per-request grant into a 0700 temp directory swept on quit and calls `shell.openPath` under a viewer-only mime allowlist — never `openExternal`, never an executable or interpretable kind, refusals in words.

**Capture is the main process's act** (D-122, D-123). The embedded view is the only surface Novus ever photographs or records: the renderer names a lane and nothing else — no URL, no window id, no path, no object key — and the main process refuses in words unless *that lane's* preview is open with a loaded page whose reporting process is live right now. A screenshot is `capturePage` on the view plus provenance read at the same moment (the process and validated origin, declared readiness, and the worktree's `git rev-parse HEAD` with a dirty flag); textual metadata passes the lane's known-secret redaction before it travels, and the pixels are stated as unscanned. A **recording** hands the view's own contents to a hidden Novus-owned recorder page through Electron's display-media handler — the page can name no source — and Chromium's own `MediaRecorder` encodes WebM; the main process owns the temp file (0700 directory, 0600 files, removed on every terminal outcome and swept at the next start), the incremental digest, the stated duration and size bounds, and the upload under the artifact grants; recorder ipc is accepted only from the capture session. A recording the app, the preview, or the encoder dies under is finalized as `interrupted` with the reason — preserved and marked, never published as an ordinary success — and a cancelled one leaves nothing anywhere. Uploads run under the initiator's own authority: a person's capture under their session, an agent-requested one under the runner credential naming the requesting execution, which the control plane verifies is that runner's own live turn.

### Repository and workspace synchronization

Git is the revision protocol between execution locations; it is not a claim that their filesystems are continuously identical. The control plane owns branch identity and expected revisions, the runner owns the checked-out working tree, and GitHub is V0's remote exchange boundary.

Provisioning contract:

1. The control plane resolves the requested base ref to an exact commit under the creator's own GitHub token (D-223) and stores immutable `base_sha`.
2. It allocates one repository-unique mission branch for the workstream and creates it at `base_sha` with a compare-and-set request. Repeating the command is idempotent only when the existing branch points to the expected SHA.
3. The provider receives a short-lived, repository-scoped credential through the supervisor, checks out that branch, and reports `checkout_head_sha` and dirty state. The harness never receives the GitHub credential.
4. The workspace becomes `ready` only when the reported revision matches the control plane's expected branch head and repository setup succeeds.

Checkpoint contract:

- The runner snapshots the Git diff and repository metadata at each safe turn boundary, before suspension, and at execution termination. Diff content is stored as a mission-scoped artifact; its digest and the workspace/remote SHAs are durable events.
- A successful execution boundary with repository changes produces an attributed checkpoint commit and pushes it to the mission branch with an expected-old-SHA guard; a clean boundary records the unchanged revision without manufacturing a commit. The control plane advances `remote_head_sha` only from the observed GitHub result, never from the runner's claim alone.
- A destroyed workspace is reconstructed from the mission branch plus the latest verified checkpoint artifact when the artifact is newer than the published branch. Provider pause/resume is an optimization, not durability.

Inbound-update contract:

- GitHub webhooks and a pre-direction remote-head check detect movement of either the mission branch or its base. Detection emits `repository.update_available`; it never mutates the workspace.
- `workspace.sync` is controller-authorized and executes only at a runner-declared safe boundary. The command includes expected `checkout_head_sha`, expected `remote_head_sha`, and the target remote SHA so stale clients cannot synchronize a different revision than the one they reviewed.
- A clean, explicitly approved fast-forward records its actor and resulting SHA. Novus never silently rebases or merges. Divergence, force-push, dirty overlap, or conflicts emit `repository.sync_failed` with both SHAs and conflicting paths; the workspace remains inspectable and further direction may be queued.
- Following a moved **base** is `base.sync` (D-144), a different act from applying a mission-branch update: the runner merges the resolved base tip into every lane's worktree — prechecked per lane, so a dirty worktree or a conflict anywhere refuses the whole act with the lane and paths named before anything moves; a merge, never a rebase, because every recorded checkpoint SHA must stay true — then reports the outcome. The control plane's route verifies the asker holds `base.sync`, that the reported lanes are exactly the mission's, that the expected pin matches (a stale room cannot move the base), and that no lane holds a live execution; it then moves every lane's `base_sha` in one transaction and records `workspace.base_synced`. A refusal after the merges walks every lane back to its recorded pre-merge head, so the pin and the worktrees never disagree.
- Uncommitted files in a developer checkout are outside the cloud runner's knowledge. A future local mirror uses a normal checkout of the mission branch and the same remote-head protocol; it does not introduce a second file-sync protocol.

Conformance tests cover idempotent branch creation, stale-SHA rejection, remote movement during a turn, clean explicit fast-forward, dirty divergence, force-push, checkpoint-before-suspend, provider loss and reconstruction, and two humans attempting sync concurrently.

**Local execution (D-032, the runner in embryo).** The desktop main process is the first runner: it keeps **one worktree per workstream** created from that workstream's mission branch (the user's checkout is never touched), runs one direction as one headless harness turn under the user's own local harness login, parses the stream into `harness.*` events, and checkpoints changes as attributed commits at the turn boundary. A machine enrols separately for every workstream of a mission it can reach, so two competing approaches are two credentials, two worktrees, two command queues and two leases on one machine — isolation by construction rather than by convention (D-074). Sessions add nothing to the runner's picture (D-083): a direction names its session, the control plane records the session on the execution and starts the turn with **that session's** `harness_session_id` as the resume point, and the runner just runs the turn it is handed — continuity is decided where the rows are. Turn-taking is the same partial unique index that has always allowed one live execution per workstream: a direction for the session whose turn is running steers it; one for a sibling session is deferred with the running session named, and the control plane dispatches the current baton holder's oldest queued direction itself when a turn reports `completed` — never after a stop, a failure, or an interruption, which are states a person reads and acts on. Everything it tells the control plane arrives through the reported-events endpoint with the actor forced server-side — claims from the machine that ran the work, exactly the trust posture the runner protocol will formalize. Direction submissions and reported activity are the same append-only mission events the receipt projects.

The **repository provider boundary** (D-031) carries the control-plane side of this contract: `listRepositories` (with the host's last-push time for freshest-first listing, D-139), `listBranches` (name, tip, default flag — capped at the host's first page, stated rather than silently paged), `resolveBase(ref) → exact SHA` for any branch, `baseStatus(ref, pinnedSha)` — current, moved with the host's own ahead count, rewritten, or missing, computed from the host's ancestry answer and cached briefly with a background refresh so the room's poll never waits on a host (D-139; local checkouts answer the same question through the desktop bridge from their own git) — and idempotent `ensureBranch(branch, fromSha)` — succeeding when the branch already exists at the expected SHA, failing with a named conflict when it exists elsewhere. Repository identity is the provider's stable id, never the name. Every provider call names the **actor** whose credential performs it (D-223): the live implementation is the user-token adapter — plain REST under the acting person's own `repo`-scoped OAuth token, so listing returns that person's whole reach (owned, collaborator, and organization repositories) and GitHub enforces their authorization on every act; a person with no stored token, or one GitHub rejects, is refused by name (`repo_token_missing`) rather than served by any shared credential. A deterministic fake (including a transiently failing repository for retry paths) exercises the identical interface, and an unconfigured deployment refuses with a named error rather than degrading. Mission creation is end-to-end idempotent via a client-supplied creation key enforced by a unique index, so retried or duplicate submissions can never mint a second mission or branch; branch outcomes (`pending → created | failed`, with retry) are durable workstream state and events, never inferred.

### Control-transfer mechanics

[PRODUCT.md](PRODUCT.md#control) defines the states; the mechanics are: the control plane marks the lease `releasing` and sends `report_boundary_request`; the runner acks at the next safe boundary (`boundary_reached`); the control plane completes the transfer by compare-and-swap and emits the events. When the workstream has no non-terminal execution it is already at a boundary: the transfer completes control-plane-side with no runner round-trip. Timeout without a boundary → the stall is visible, `force_interrupt` becomes available to the lease holder or Mission Admin, and its use is a logged event. An un-acked transfer past its timeout reverts visibly; it never half-applies.

## Harness protocol

The adapter lives on the runner. It speaks the harness's native interface inward (CLI stream, ACP, whatever the harness offers) and the Novus runner protocol outward.

**Normalizable (the adapter contract requires):** start/stop; direction in (text with attribution context); event stream out — assistant summaries, tool activity, turn boundaries; exit status; diff extraction **via git**, never via harness-reported file lists.

**Not normalizable (passed through, never faked):**
- *Approval prompts*: a first-class approval event and a typed response channel. Novus routes it to the lease holder; it does not flatten harness permission models to a lowest common denominator. **Implemented for Claude Code** (D-062) over its stdio control protocol: the CLI is run with `--input-format stream-json --permission-prompt-tool stdio`, writes a `control_request` and blocks, and Novus answers on stdin. The payload is *not* passed through opaquely — the raw tool input is read and dropped on the machine that read it, and what becomes durable is a bounded, path-masked, value-redacted summary composed from named fields, because a `Write` carries the whole file in its input and a durable row is shown to every participant.
  The permission policy is **pinned by Novus, not inherited from the host**: `--setting-sources ""` and `--permission-mode manual`, so a `.claude/settings.json` in the worktree cannot decide what gets asked. The decisive reason is that the agent can write that file — a supervised turn that creates one grants itself standing permission for the next. The measured cost was that the repository's `CLAUDE.md` no longer loads; it is carried explicitly with `--append-system-prompt-file`, resolved through `realpath` into the worktree and bounded, which needs no setting source (D-064). A project's `.claude/skills` are carried the same explicit way (D-118, the version D-072's revisit clause named): the runner publishes the worktree's skill manifest for review, and a turn is dispatched with the lane's person-enabled list pinned; at spawn the runner composes a **skills-only plugin directory** of its own — `.claude-plugin/plugin.json` authored by Novus, plus one SKILL.md per enabled skill, each resolved through `realpath` into the worktree, regular, bounded, and required to hash to exactly the digest the person approved, the verified bytes being the written bytes — and passes it with `--plugin-dir`. Since D-193 there is no enabled set to check against: the runner **discovers at spawn** and composes everything the worktree declares (`.claude/skills`, `.claude/commands`) together with everything the operator's own config dir holds, and `execution.running` records each carried entry as `{name, digest}` — the account of which bytes reached the harness, in place of the approval that used to gate them. The bounds that decide what is loadable at all are unchanged: name grammar, `realpath` containment inside the worktree for repository content, regular file, non-empty, size-capped, verified bytes written. Hooks, `.mcp.json`, and agents are still never written into the composed directory, so D-072's refusal remains structure. Extension **labels** sit beside all of this and touch none of it (D-195): `extension_labels` holds an organization's own vocabulary (name unique per organization, case-insensitively; colour naming a token), `extension_label_assignments` keys one wearing by the extension's name, its collection, and — for repository content — its repository, and both are served on the mission detail beside the manifests they describe. Labels are guarded by `skills.set` and are deliberately **not** event-recorded: they change nothing about what a turn is handed, so they are not part of what happened to the work. The **machine's own** user-level servers (D-198) ride the same road with a second key: `machine-mcp.ts` reads the CLI's own `~/.claude.json` (or `$CLAUDE_CONFIG_DIR/.claude.json`), publishes redacted summaries (`declared_machine_mcp` — env names, masked secretish flag values, digest over the full local declaration), and the `/machine-mcp` route requires `mcp.set` **and** the caller to be the runner row's owner, recording the acknowledged consequence verbatim on `machine-mcp.changed`. At spawn the enabled entries are re-read locally, digest-verified, and merged into the same strict config beside the project's — values never crossing the wire in either direction (D-041), collisions with project names dropped with the reason stated. **MCP servers are the exception and keep the full publish-review-enable road** (D-119): a server is a program this machine runs and new tools the agent may call, not instructions, so its manifest, its `mcp.set` tier, its reviewed digest, and its strict Novus-authored config all stand. Skills are instructions, never authority: every tool call a skill-bearing turn makes still reaches this router. The runner machine's own user-level skills (`$CLAUDE_CONFIG_DIR`, else `~/.claude`) are published the same way — a `globalSkills` list on the same `workspace.declared` event, stored in `workspaces.declared_global_skills` — and, since **they never load by themselves under the pinned policy** (D-191, measured against 2.1.237, correcting what D-118 assumed), they are enabled at a reviewed digest through their own route (`enabled_global_skills`, `global-skills.changed`, `skills.set`), pinned at dispatch, and composed into the same directory from the operator's own config dir. The worktree containment rule does not extend to that directory — it is the person's own, outside any repository — while every other bound does: regular file, non-empty, size-capped, digest-verified, verified bytes written.
  A project's MCP servers are governed the same way, one tier up (D-119): the runner publishes the worktree's `.mcp.json` as a bounded manifest, and a turn is handed only the servers a Mission Admin enabled — re-derived from the worktree at spawn, digest-checked against the approval, and written into a config **Novus authors**, passed with `--mcp-config` and `--strict-mcp-config` so the composed file is the CLI's entire MCP world (probed on `claude 2.1.229`: exactly the named servers load, nothing else) — **except when the turn's owner has lent an account** (D-217), where `--strict-mcp-config` is omitted so the CLI injects its own claude.ai connectors, and every connector it would inject that was not lent is removed from the model's tool list with `--disallowedTools mcp__{id}__*`. That relaxation rests on a measurement that corrected D-198: `--setting-sources ""` **alone** keeps every agent-writable file out (a worktree's `.mcp.json`, `.claude/settings.json`, and `.claude/settings.local.json` all load nothing without it), so strict was belt over that pin rather than the pin itself; the composed config still carries exactly the reviewed project and machine servers plus the `novus` endpoint, and the connectors ride beside it, not through it. Which accounts are lent is resolved on the machine at spawn from two machine-local files — the person's per-connector On/Off, and a cached enumeration of what `claude mcp list` last reported — never pinned by the control plane, because lending is the person's own standing choice and not a mission setting. A lent connector's tool call reaches the router like every other, and the router sends it to the room under **every** profile including `dont_ask`, because it spends the owner's own account; the control plane's respond route then accepts only the runner owner's answer, reading the `executions.connectors` the turn recorded to tell a lent-account question from any other. Since D-123 that composed world carries exactly one first-party entry beside the enabled project servers: the **`novus` endpoint** — a loopback HTTP MCP server inside the Electron main process, addressed with a per-turn bearer token, exposing three first-party tools: the screenshot capture (D-123); `push_branch` (D-140), which pushes the lane's latest checkpoint through the identical hardened path a person's publish rides — mission branch only, never `--force`, a write-scoped credential minted per operation by the control plane and forgotten; and `declare_run_command` (D-156), which writes a run declaration into `.novus/settings.toml` through the same schema-validated serializer a person's confirm uses — the configuration format is Novus's own, so the file an agent declares through is valid by construction, an existing unreadable file is refused in words rather than replaced, and declaring runs nothing: the Run control stays a person's act. Since D-218 the endpoint also carries the **fenced-browser tools** — `browser_navigate`, `browser_click`, `browser_type`, `browser_press`, `browser_read` — which drive the lane's own embedded preview (the isolated loopback webview of D-163) from the main process: `browser_navigate` is confined to the approved origin by the same gate the preview opens under, the acting and reading verbs refuse in words while the page is off that origin (a person may browse the surface elsewhere, D-224 — the agent may not act there, and same-origin navigation is its one way home), and every act refuses in words when no page is showing. These differ from the one-shot tools in their grant: a **per-turn browser session** rather than a one-shot per call. A person's first browse of the turn is answered at the router; an allow mints the session, and every later browser call rides it without another card — one approval covers the turn — while a person's mid-turn cut-off (`preview.stopBrowsing`) revokes the session so the next call is refused, sticky for the turn, without ending it. The endpoint verifies the session still stands at each call, so a cut-off refuses even an action the router last allowed. Raw computer use (D-218) adds `computer_screenshot`, `computer_move`, `computer_click`, `computer_type`, `computer_key`, and `computer_scroll` on a second per-turn session, and is the most guarded surface in the product. Its guardrail is four structural layers plus a weak fifth: a **machine-local opt-in** off by default, which the agent cannot reach and which the router checks first — a Mac that has not consented refuses a computer tool outright, never even asking; the **structural fence** in the main process, which refuses any pointer action landing on a Novus window, typing while Novus is frontmost, and any keypress that would land in Novus — except the two ⌘-space / ⌘-tab shortcuts, which only move focus *away* from Novus and are the agent's one door off it (the honest limit remains: an agent that first backgrounds Novus escapes the fence); the **un-self-renewable grant** (the session, minted only by a person's approval); the **mid-turn cut-off** (`preview.stopComputerUse`, and turning the opt-in off, both revoking live); and a **Novus-injected `--append-system-prompt` directive** telling a well-behaved model to never touch Novus — instructions, not authority (D-062), stated as the last line. The actual OS input and screen capture live behind a `DesktopDriver` seam so every guardrail is proven against a fake driver; the native backend captures the screen through Electron's own `desktopCapturer` and synthesizes input through **`@nut-tree-fork/nut-js`, an optional native dependency**: it loads under Electron 37 and moves the real mouse once macOS Accessibility permission is granted, while a machine without the module (or its prebuild) degrades to eyes-only — the `require` is caught, `available()` reads false, acting refuses in words. Accessibility is the OS gate only the owner can grant; the settings card reads its status and can open the pane. A visible always-on-top click-through overlay marks where the agent acts. The name `novus` is reserved at discovery, so no project declaration can impersonate it. Each tool call rides this router as every MCP tool does — a person's question under every profile short of `dont_ask` — and an *allow* additionally mints a one-shot, short-lived grant at the runner **for that tool alone** (a capture allow spends nothing of push); the endpoint acts only when a live turn's token **and** an unspent grant for the named tool stand together, then applies every check a person's own act faces. The token is a request-channel identifier, never authority: learning it (the config is a file) grants nothing without a routed approval. An enabled server's tools reach this router like every tool, and the router treats `mcp__{server}__*` as it treats a shell command: their effects are declared nowhere Novus can read, so `auto` never answers one — only `dont_ask` does, on the record. A server's process runs inside the harness environment (D-041), which holds no project secrets and no runner credential; a remote server is admitted only over https away from loopback, with no credentials in its address — the one network restriction a local runner can honestly enforce, and the manifest refuses what it cannot.
  A lane's **permission profile** (D-115) never loosens this wire. Every profile runs under the same pinned flags with the channel open; the profile is the runner's own answer ladder at the router — containment (a read turn denied whatever the lane trusts, D-095), then `plan`'s deny-all, then a scope's verdict (D-097), then the profile's allows, then the room — with every profile-decided answer reported as `approval.policy`, carrying the same bounded, redacted summary a card would have. The CLI's `acceptEdits`, `auto`, `dontAsk`, and `bypassPermissions` modes are never passed: each makes the CLI act without asking, and everything above rides the asking. The one flag a profile changes is `plan`'s — `--permission-mode plan`, the harness's own plan mode — and the router still denies every privileged act a plan turn asks for, so the flag is behaviour and the router is the guarantee.
  A pending approval **is** a safe execution boundary ([PRODUCT.md](PRODUCT.md#control)), declared by the runner when it asks. Without that, a control handoff accepted while the harness is blocked waits for a boundary that can never arrive, since a turn blocked on stdin never exits.
- *Approvals, the Codex dialect (D-230)*: **implemented for Codex** over `codex app-server` JSON-RPC, the protocol taken from the binary's own `generate-json-schema` (0.145.0). The runner speaks `initialize` → `thread/start` (or `thread/resume {threadId}` — the thread id is the session continuity the workstream records — falling back once, openly fresh, when the server no longer holds it) → `turn/start`, and the notification stream is normalized into the same runner events: `item/agentMessage` completions become `harness.text`, tool items become `harness.tool`, completed `commandExecution` items become `verification.observed` through the same command classifier, `thread/tokenUsage/updated` + `turn/completed` become `harness.usage` and the result. Approvals arrive as server-initiated requests (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`) and are lifted into the identical control-message shape the ladder judges for Claude — one ladder, two dialects — answered `{decision: accept|decline}` and nothing else: `acceptForSession` and the execpolicy amendment are standing grants nobody gave, discarded exactly as Claude's `permission_suggestions` are (D-056's rule, this wire). The pinning is per-thread parameters and stricter than flags: `approvalPolicy: "untrusted"` (every act asks), `approvalsReviewer: "user"` (never `auto_review` — the CLI approving itself), and `sandbox: "workspace-write"` for write turns, `"read-only"` for read-alongside turns, which makes D-095's containment structural here. The interrupt is `turn/interrupt` with the same grace-then-signal escalation. What Codex does not carry, stated rather than faked (D-230's manifest honesty): no Novus-composed skills or slash commands (Codex reads the worktree's own `AGENTS.md` natively), no `novus` capture endpoint, no lent connectors, no browser or computer surfaces — the execution record shows each as absent; and a decline crosses this wire without its reason (the grammar has none), the reason staying durable on Novus's own record.
- *Pause/resume and session continuity*: harness-dependent. Where a harness cannot resume, "pause" degrades to stop-at-boundary + restart-with-context, and the adapter declares which semantics it provides. The product never promises uniform pause behavior ([PRODUCT.md](PRODUCT.md#the-harness-boundary)).
- *Mid-turn steering*: adapters declare `steer: mid-turn | at-boundary`. Direction "Applied" is control-plane state marked on harness acknowledgment, per [PRODUCT.md](PRODUCT.md#direction).
- *Token/cost reporting*: opaque optional metadata in V0. Nothing is billed from it, nothing is stopped by it, and no ceiling is derived from it (D-034). Recorded per turn as the harness's own claim and summed onto the execution; a figure the harness did not report stays null rather than becoming zero (D-071).
- *Optional harness flags*: an adapter may ask for capabilities it can run without — subagent forwarding is the first — and a harness that refuses one by name is retried once without it. The flags that carry the permission guarantee are never in that set: a harness that will not route approvals fails the execution outright rather than running unsupervised (D-062, D-071).

Adapters declare a capability manifest (steer granularity, resume support, approval model, verification hooks) at registration; the control plane and clients render from the manifest instead of assuming. The manifest is re-validated at every execution start — a harness auto-update that breaks an adapter fails the start with a named error rather than producing undefined behavior.

## GitHub ingestion

The control plane ingests GitHub webhooks — pull-request state, reviews, check runs — and normalizes them into mission events with `actor.kind: external`. This is data ingestion, not execution: payloads are parsed and recorded; nothing runs. CI check results arrive this way and are recorded as evidence claims attributed to the CI environment, exactly as runner-reported verification is attributed to its runner. Polling is the fallback when webhook delivery lapses — and for the local-first deployment, which has no public endpoint a webhook could reach, the poll **is** the transport (D-099): a sweep beside the reliability sweep refreshes every open pull request — state, draft flag, mergeability, review threads — and records what changed as external-actor events. **The webhook receiver exists (D-101)**: `POST /webhooks/github`, present only when a shared secret is configured, verifying `X-Hub-Signature-256` over the raw bytes in constant time, and answering a genuine knock by syncing exactly the named request through the same per-row path the poll uses — the payload names what to re-read and is never applied as state itself. The hook is a plain repository or organization webhook sharing that secret; the poll reads each row under its own person's stored token (the pull's creator — a row whose person holds no token stays visibly unsynced until they sign in again, D-223).

Pushing is the runner's act, never the control plane's: a `push_branch` command pushes the decided revision itself (`{sha}:refs/heads/{branch}`) with a per-operation, write-scoped credential minted separately from the read-scoped clone credential, injected through the same pipe, and never stored. There is no force push anywhere; a non-fast-forward is surfaced in words.

## Authentication

- Users authenticate to the control plane; sessions are server-side with revocation (httpOnly cookie for browser, secure token store for desktop). Identity is GitHub OAuth with first-party sessions (D-019); the database stores only a hash of the session token.
- **Desktop sign-in flow (D-027):** the desktop app asks the control plane to start a flow, opens the authorization URL in the system browser, and polls a single-use claim endpoint keyed by the flow's state nonce. The browser leg completes at a control-plane callback; the claim hands the session token to the Electron main process exactly once. The token lives only in the main process — encrypted at rest with OS-backed storage (`safeStorage`), never written in plaintext, and never crossing the IPC bridge to the renderer.
- **GitHub access is the person's own (D-223, reversing the App split):** the `repo`-scoped OAuth token stored at sign-in is both identity **and** repository access — every provider call, clone, push, and PR act is performed with the acting person's own token, so GitHub enforces per-person authorization and shows the person as the author. There is no server-held GitHub credential; a machine acting with no person present is exactly the case D-223's revisit clause reserves for a future server identity.
- Invitations: single-use, expiring, mission-scoped tokens; redemption requires an authenticated user and creates the Participant row ([PRODUCT.md](PRODUCT.md#domain-model)).
- Runners authenticate with credentials scoped to (org, mission, workstream, runner), stored only as hashes, expiring and revocable (D-035). The local runner enrolls explicitly: the host desktop registers for a workstream over its owner's authenticated session and receives the credential exactly once, into the Electron main process — never the renderer, never an event payload, never a log line. Cloud runners will receive their initial credential injected at workspace creation; the verification path is the same either way.

## Authorization

Capabilities are enforced in exactly one place: a server-side check on every mutating command — including approval responses — computed per the capability model in [PRODUCT.md](PRODUCT.md#roles-and-capabilities) (role ∪ lease), evaluated against current durable state (current lease id, mission state) at command time. Where a mission holds more than one workstream, a request that names a lane — a direction, a workspace command, or a mission read — is resolved against **that lane's** lease and state; a lane that does not belong to the mission is answered "no such mission", never with the default lane's authority under the wrong name (D-074, D-080). The same rule holds for requests that arrive **through a row** rather than a mission id: resolving or cancelling a queued direction is judged against the direction's own lane, answering an approval against the approval's own lane, and a stop against the lane it names on the wire (D-083). A session named in a request must belong to the named lane, or it is answered as not found — naming someone else's session never widens what you can do to your own. Lease transitions are compare-and-swap on lease id + state. Per-mission commands are serialized through a per-mission ordering point so concurrent conflicting commands (two accepts, action during lease expiry) resolve deterministically: one wins, the loser receives an explicit rejection event. UI capability lists are advisory rendering data. Any code path where the client's claim decides a privileged action is a security bug, not a style issue.

## Persistence

- One relational database owns all control-plane state, including the event log (append-only tables). Presence keeps no history anywhere: one overwritten `last_seen_at` per participant (D-091), no events, no receipts.
- Artifacts (screenshots and recordings today; transcripts, logs, and receipt exports later) live in blob storage referenced by rows; blobs inherit mission scoping and retention. The store is D-022's S3-compatible interface, realized by D-122 as two adapters behind one boundary: the **local store** — blobs on the control plane's own disk, served over HTTP routes whose only authorization is an expiring HMAC signature — is the local-first deployment's store and the deterministic test adapter; the **S3 adapter** (SigV4 presigned PUT/GET/HEAD, the upload signature pinning `x-amz-content-sha256`) is opt-in via environment and unproven live until credentials exist. Unconfigured storage refuses by name (`artifact_store_unconfigured`); nothing degrades silently.
- **Attached images** (D-150) reuse that flow exactly, with two differences and no third. They are begun on `POST /missions/:missionId/attachments` under `direction.submit` rather than `artifact.capture` — illustrating what you mean is part of saying it — and they require **no runner**, because a person's own file needs no machine holding the workspace. The row records `kind: attachment` and `capture_source: upload`, with every capture-provenance column null: Novus captured nothing and states so. The client normalizes before uploading — a closed MIME allowlist decided by the file's own signature rather than its name, the longest edge scaled to 1568px, a 5MB ceiling after that for images and 10MB for documents (a PDF is carried whole or refused; there is no smaller-but-still-readable version of one) — so an attachment costs the store, the wire, and the harness's context what a readable file costs. The allowlist is settled by probing the harness, not by reading a format list (D-151): PNG, JPEG, GIF and WebP travel as image blocks and PDF as a document block because each was observed to work; HEIC, TIFF and BMP are decoded to PNG first because HEIC passed through does not fail — it makes the model answer confidently about a picture it could not decode. `direction_attachments` fixes what a direction was submitted carrying, in the person's own order, inside the submitting transaction; a direction naming an image that is not this mission's, not an attachment, not yet verified, or named twice is refused in words rather than submitted. The machine running the turn fetches each blob through `POST /runner/attachments/:artifactId/view`, whose mission clause is what makes the runner credential's scoping do the work, and hands the bytes to the harness as **image or document content blocks in the turn's first message**, or — for a file the model cannot read (D-153) — writes it into the lane's worktree under `.novus/attachments/` and names the path in its own text block beside the person's words. A staged file is kept out of the mission's history twice over: the directory is added to `.git/info/exclude`, which is per clone and never committed so the project's own `.gitignore` is untouched, and the checkpoint refuses the path outright, so a missing exclude file cannot put a person's file into a branch. It is written `0600` and never executable, because it lands where an agent runs shell commands — so nothing is written into the worktree, and no checkpoint can sweep an attachment in.
- **Transcripts** (D-173) ride the same begin route with one extra claim: `transcriptOf` names a session, which must be the lane's own or the answer is not-found, and the MIME must be `text/markdown` or the claim is refused. The row lands as `kind: transcript` with `csn_id` set to the **source** chat — so the artifact view's "View in conversation" opens what was projected — and its label derived server-side from that chat's own title, never from the client's filename, which a client could otherwise spoof. The bytes are the renderer's own projection of the source session's feed: the one feed derivation the room renders from is the one that projects, so what a person read and what the new chat receives cannot disagree. Downstream, a transcript is an ordinary staged attachment: `direction_attachments` accepts the kind alongside `attachment`, and the runner writes it under `.novus/attachments/` with every protection above.
- The artifact upload/download flow: the control plane generates and scopes every object key; a capture *begins* by promising kind, MIME, length, and SHA-256, and receives a short-lived signed upload grant bound to exactly that promise; the store refuses bytes that do not match; *completion* moves a row to `available` only on the store's own confirmation of length and digest — never on the uploader's word — and a mismatch fails the row terminally with the reason. Store credentials live in the control plane alone and reach no runner, client, or harness; signed URLs are minted per request, expire in minutes, and are never stored, logged, or written into an event or receipt. Viewing is a mission-authorized route that mints a fresh temporary URL each time — reads use the same mission authorization boundary as everything else, so neither an artifact id nor an object key retrieves anything by itself. A pending upload the reliability sweep finds abandoned is failed by name.
- Receipts are stored as snapshots plus the projecting event range; regeneration must be deterministic over current event state (same events → same receipt). Redaction (D-014) cascades: affected snapshots are re-projected and replaced, and the re-projection is itself a recorded event.
- A control lease's heartbeat is the holder's client being observed. Reading the mission renews it (D-051), and an open client stream renews it too (D-149) — a connection the holder's machine is keeping open is the better evidence of presence, and it is what keeps a lease alive in a room nobody is typing in.
- Vendor selection (specific database, blob store, realtime transport) is deliberately not made here; interfaces first, vendors in DECISIONS.md at implementation time (D-012).

## Failure handling

Named failure modes with defined behavior — these are contracts, not aspirations:

1. **Runner dies mid-execution** (crash/OOM): heartbeat lapse → execution `interrupted`; mission shows it; resume-or-restart is a human choice preserved in history.
2. **Control transfer during a partition**: lease transfer is control-plane-authoritative with runner ack; un-acked transfer times out and reverts visibly.
3. **Workspace provisioning fails**: terminal `failed` state with the provider error surfaced; retry = new workspace.
4. **Direction while the harness is non-receptive**: queued durably, applied at a receptive point, superseded explicitly — never silently dropped.
5. **Simultaneous conflicting commands**: per-mission serialization; losers get explicit rejection events (see [Authorization](#authorization)).
6. **Event overflow during a long disconnect**: gap marker; the receipt states the gap.
7. **Harness hangs** (endless tool call): watchdog → execution `stalled`; `force_interrupt` available and logged.
8. **GitHub token expiry/revocation or force-push to the mission branch**: repository-sync error state with human-visible remediation; no silent retry loops and no mutation from a stale expected SHA.
9. **Controller disconnects and does not return**: lease TTL expiry → the workstream has no controller and no privileged command can be issued until someone claims or is granted the lease. The already-authorized execution keeps running (D-034); authority lapsing is not a stop signal. Claim/revoke path per [PRODUCT.md](PRODUCT.md#control).
14. **Host desktop quits during a local execution**: in-flight turns are killed with their process trees, the execution is recorded `interrupted` with the reason, and the outbox flushes before exit — no orphan process, and no room left claiming "running" forever (D-034).
10. **Control plane unavailable**: the runner continues its current execution under the last applied direction, buffers events, and refuses privileged transitions (transfers, new executions) until reconnect.
11. **Workspace suspended or destroyed while a transfer or queued direction is pending**: the offer moves to `failed` visibly; queued direction stays queued for the workstream's next workspace and execution.
12. **Mission branch or workspace conflicts with a remote update**: repository-sync error state with both revisions and conflicting paths preserved; resolving the conflict is directed work, never a silent automatic rebase or filesystem overwrite.
13. **Invitation redeemed after the mission reached a terminal state**: redemption succeeds as read access — the participant joins as Viewer and sees history and receipt; no operational verbs.

## Deployment modes

- **Shipped first**: a Novus-hosted control plane, a downloadable desktop client (D-018), and the **host desktop as the runner** — registered per workstream, credentialed, and speaking the runner protocol against local repositories (D-032, D-035). Local execution is the first real surface, not a fallback.
- **Next, on the same protocol**: Novus-managed cloud runners on one sandbox provider (D-023), which is what makes a mission survive a closed laptop and remain the multiplayer default (D-002).
- **Kept-possible by the protocol**: enterprise runner (customer infrastructure dials out) and third-party sandbox providers behind the execution-provider interface. The conformance suite ([Testing strategy](#testing-strategy)) is what keeps these honest.

**The deployed control plane's shape (D-221).** The server binds loopback by default — the local-first deployment serves one machine and must not be reachable from the network by accident. Deploying it is three deliberate settings and a container: `NOVUS_CP_HOST` widens the bind (typically `0.0.0.0` inside a container, where loopback would mean unreachable); `NOVUS_CP_PUBLIC_URL` is the https URL clients, the OAuth callback, and the App webhook all derive from — nothing else encodes the address; and TLS is terminated **in front** of the process (Caddy, nginx, or a cloud load balancer), never inside it — the control plane speaks plain HTTP to its proxy, and sessions are bearer tokens, so transport security is entirely the proxy's TLS. The image (`apps/control-plane/deploy/Dockerfile`) runs the TypeScript directly and migrates on boot, exactly as `pnpm dev` does; the compose file beside it pairs it with PostgreSQL and a volume-backed local artifact store, with the S3 adapter the opt-in for object storage. A desktop client reaches any deployment through `NOVUS_CP_URL` — or, for a packaged app whose Finder launch has no environment, through one plain file a person writes once: `{userData}/control-plane.url`, holding a single http(s) URL (D-222); the environment variable wins where both exist, and the loopback default serves local-first. The GitHub OAuth App's callback must name the public URL — a deployment is a different OAuth App (or an updated callback), never a shared secret with the loopback one.

**The packaged desktop client (D-222).** `pnpm package` in `apps/desktop` produces the installable app with electron-builder — the same `dist-electron`/`dist-renderer` bytes `pnpm start` runs, plus production `node_modules`, with the pty's prebuilt binary unpacked from the asar. The build is deliberately unsigned (`identity: null`): Gatekeeper shows its warning and the README's right-click-Open note is the answer, until a Developer ID exists. Test hooks (`NOVUS_AUTH_AUTOVISIT`, `NOVUS_FAKE_IDENTITY`, `NOVUS_USER_DATA_DIR`) refuse packaged builds by construction (D-027), so a packaged app is always the real product against the machine's own userData.

## Observability

- Every protocol edge (client command, runner command, runner event) is traced with mission-scoped correlation ids.
- Control-plane metrics: command latency, event lag (runner `occurred_at` → client visibility), lease-transition outcomes, transfer-timeout rate, reconnection/backfill counts, gap-marker rate.
- The event log is itself the primary audit surface; operational logging never becomes a second source of product truth.
- No customer code, secrets, or harness transcripts in operational logs.

## Testing strategy

- **Contract tests** on the runner protocol and harness-adapter manifest: a conformance suite any runner or adapter must pass — this suite, not optimism, is what "runner-agnostic" means.
- **State-machine tests**: exhaustive transition tables for lease/request/offer, direction, mission state, workspace lifecycle — including the race cases named in PRODUCT.md (simultaneous requests, expiry during action, accept-then-disconnect).
- **Deterministic replay tests**: receipt projection over recorded event logs; same log, same receipt, byte-for-byte.
- **Integration tests** with a fake harness adapter (scripted activity, boundaries, approvals) so multiplayer flows are tested without model calls.
- **Repository-continuity tests**: branch creation from an exact SHA, checkpoint/push guards, update detection, explicit sync at a boundary, conflict preservation, and reconstruction in a replacement workspace.
- **Live proof**: the Golden V0 workflow executed by two real clients against a real deployment is the only thing that marks M1 complete ([PROGRESS.md](PROGRESS.md)); deterministic suites never substitute for it.
