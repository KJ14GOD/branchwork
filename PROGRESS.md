# Progress

## Current milestone

**Two people operating one real mission (D-034 … D-037).** Live today in the desktop app: sign in with GitHub, open a local project, and direct real Claude Code in a dedicated mission worktree under a credentialed local runner. The turn's changes are recorded as git-derived evidence, a follow-up direction resumes the same harness session, and a second authenticated person can join by invitation from another desktop, see the identical durable mission, queue an attributed direction, take the control baton through an explicit request-offer-accept handshake, and have their direction executed by the first person's machine. Closing and reopening either client reconstructs participants, directions, control history, checkpoints, and evidence.

Cloud execution, Codex, review, pull-request tracking, and receipts remain Not started.

## Status rules

- Every status is one of: **Not started**, **Partial**, **Implemented**, **Blocked**.
- **Implemented** and **Partial** require an Evidence line: a command with observed output, or a link to an artifact a human can inspect. Documentation is never evidence of functionality. Deterministic tests are evidence that the tested path works deterministically — they are never "live proof" of end-to-end behaviour; only a real client exercising a real system is.
- The Golden V0 workflow ([README.md](README.md#the-golden-v0-workflow)) is the milestone gate for the first implementation: it is not done until two real clients execute all twenty steps.

## Known gaps

- **No lease expiry.** A control lease ends by transfer or by Mission Admin revocation. A controller who disappears holds the baton until someone revokes it; the TTL and heartbeat described in PRODUCT.md#control are not implemented.
- **`stop_execution` queues behind the turn it should interrupt.** The runner agent chains commands per workstream, so Stop cannot reach a running Claude turn until that turn ends on its own. Found while building the workspace supervisor, which bypasses the chain for its own stop; the execution path was left alone deliberately rather than widened into.
- **A local preview cannot be opened from Novus.** Electron's window-open handler forwards only `https:`, so a `http://localhost:3100` preview is shown as selectable text rather than opened. Opening it needs a bridge verb that does not exist.
- **No interactive terminal.** Contracted in DESIGN.md and D-042 and not built: it needs a native PTY module and an Electron rebuild.
- **No heartbeat watchdog on the runner.** A host that is killed rather than quitted leaves its execution non-terminal; the room shows *Runner offline* and a participant must stop the execution to free the workstream. ARCHITECTURE's failure case 1 is documented, not built.
- **The runner transport is polling.** D-021 chose control-plane WebSockets and D-035 records polling as the shipped transport with identical semantics. Event latency is bounded by the two-second poll.
- **No approval routing.** `needs_approval` exists in the execution and mission state models and is never entered; Claude Code runs under `--permission-mode acceptEdits`, so a permission prompt never reaches a human. This is the largest honesty gap in the harness boundary and blocks any claim about supervised autonomy.
- **Verification is observation-only.** Novus records checks the harness happened to run. It cannot run a check itself, re-run a failed one, or ingest CI.
- **One workstream per mission**, one repository per mission, and no terminal mission lifecycle: a mission cannot be completed or cancelled.
- **Evidence diffs are stored inline** in PostgreSQL rather than in the artifact store D-022 selected, bounded to 150 files and 12 000 characters per file per checkpoint (D-037). A turn touching more files reports the first 150; the commit SHA remains the complete record.
- **Worktrees are never removed** after a mission ends, and there is no cleanup policy for terminal or archived missions.
- The desktop app runs from `pnpm dev` only; there is no packaged, signed, downloadable build, and no Windows or Linux run has happened.
- The light theme is still not proven on rendered screens; every screenshot is dark, macOS, and at three window sizes only.
- Egress default-deny via provider IP rules is proven unworkable (D-024); the egress proxy that replaces it does not exist even as a specification.
- The repository-continuity contract (D-025) is only partly implemented: mission branches, base pinning, and checkpoints exist; remote-update detection, explicit synchronization, conflict presentation, and replacement-workspace reconstruction do not.

## Blocked

- The authenticated-harness leg of the provider spike is blocked on explicit opt-in to transmit provider API keys to a disposable sandbox and on an Anthropic API key that is not present on this machine. Only the account holder can provide these.

Next step: the interactive terminal, then the runner heartbeat watchdog and lease expiry, then approval routing — the two failure paths PRODUCT.md and ARCHITECTURE.md promise and this build does not yet keep — followed by approval routing, which is what would let Novus claim supervised autonomy honestly.
