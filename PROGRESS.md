# Progress

## Current milestone

**Two people operating one real mission (D-034 … D-037).** Live today in the desktop app: sign in with GitHub, open a local project, and direct real Claude Code in a dedicated mission worktree under a credentialed local runner. The turn's changes are recorded as git-derived evidence, a follow-up direction resumes the same harness session, and a second authenticated person can join by invitation from another desktop, see the identical durable mission, queue an attributed direction, take the control baton through an explicit request-offer-accept handshake, and have their direction executed by the first person's machine. Closing and reopening either client reconstructs participants, directions, control history, checkpoints, and evidence.

**Terminal and runtime trust (D-043 … D-046)** lands on top of it, proven in the app on 2026-08-03: an interactive terminal on a real PTY that opens in the mission worktree and nowhere else and renders what real programs actually print; a dock that is the terminal alone (D-049), with setup, run, and check output read in the evidence panel's Output section on the machine that produced it (D-050); a setup flow a person reviews, saves, and runs; a declared check invoked on a click whose evidence is bound to the revision it tested; project-stated deadlines with a timed-out outcome that is not a failure; readiness as a declared signal rather than an assumption; secret values supplied at the machine that has them; and a loopback-only preview bridge. The command a participant authorizes is pinned to what they saw, so a turn editing the project's configuration cannot change what their click runs.

Cloud execution, Codex, review, pull-request tracking, approval routing, and receipts remain Not started.

## Status rules

- Every status is one of: **Not started**, **Partial**, **Implemented**, **Blocked**.
- **Implemented** and **Partial** require an Evidence line: a command with observed output, or a link to an artifact a human can inspect. Documentation is never evidence of functionality.
- Evidence comes in tiers, and a claim never borrows a higher one than it has earned:

  | Tier | What it means |
  | --- | --- |
  | **Tested** | A deterministic suite exercises the path. Real processes, real git, real PostgreSQL where the suite says so — but a fake provider or a scripted harness stands in for the outside world. Never live proof. |
  | **Proven in the app** | An Electron end-to-end run drives the real interface in a real window. What a person can actually reach, as opposed to what the modules underneath can do. |
  | **Proven live** | Exercised against the real GitHub or the real Claude Code binary, with the observed result recorded. |
  | **Partial** | Some of the capability is real and some is not, and the line says which. |
  | **Not started** | No implementation. |

- A deterministic suite passing against a fake provider is **Tested**, never "live". A module working is not the same as a person being able to reach it: code that no interface exposes is **Partial** at best, and the line says what is unreachable.
- The Golden V0 workflow ([README.md](README.md#the-golden-v0-workflow)) is the milestone gate for the first implementation: it is not done until two real clients execute all twenty steps.

## Critical verbs, and what proves each one is wired

Three faults have reached real sessions because a verb was written, tested, and
never called (D-051). The check that would have caught all three is a test that
enters where the product enters, so every verb below names one. A unit test that
imports the function and calls it is not in this column, on purpose — that is
the kind of test all three faults already had (D-054).

| Runner heartbeat | the runner's own poll | `runner.test.ts` — liveness is a side effect of polling; a runner silent past the threshold has its execution ended by the sweep |

## Known gaps

- **The live GitHub runtime proof is written but has not been run.** `apps/desktop/e2e/live-github.spec.ts` selects a real repository through the interface, creates a mission, waits for the runner to fetch it, checks the worktree is on the mission branch at the exact recorded base, runs a declared command and a check on it, then independently asserts that no installation token is in `.git/config`, anywhere under the machine's Novus state, in any event payload, or in any recorded check — and that a user session cannot ask for one. It is opt-in and cannot be otherwise: repository access comes from a GitHub App installation bound to a real organization, and that binding is created by a person signing in through their own browser, so the run borrows a profile that is already signed in. Until somebody runs it, "GitHub repositories run locally" stays Partial and the clone path is **Tested**, not proven live.

  ```
  NOVUS_LIVE_GITHUB=1 NOVUS_LIVE_PROFILE="$HOME/Library/Application Support/Novus" \
  NOVUS_LIVE_REPO=owner/name \
  pnpm --filter @novus/desktop exec vitest run --config e2e/vitest.config.ts e2e/live-github.spec.ts
  ```
- **The desktop suite's intermittent failure was a real bug, and is fixed.** It runs files one at a time, and 239 desktop tests passed on a quiet machine while `workspace-clone.test.ts` failed intermittently under load. The gate used to run every step into `/dev/null`, so a failure named the command and nothing else; that was fixed first, and the output then said `fatal: cannot change to '.../worktrees/msn_…': No such file or directory` — a worktree deleted while its creator was still using it. Two callers ask for the same worktree by design (the runner's turn path, and a terminal or file listing the person just opened), and preparation read "is it there" and then deleted what it found, so the loser removed the winner's worktree. The user-visible form is *"This workspace could not be created"*, reported from a real session and read at the time as a GitHub problem. Preparation is now serialised per worktree path (D-058). Proven by seeding the failure — bypassing the serialisation makes the new six-caller test fail with that exact message — and by four consecutive clean runs of a file that had failed one in three.
- **Stop reaches a turn on a machine that is running it, and not one that is starting it.** Fixed and proven in this slice (D-053) — what remains is the crash window: a runner killed between acknowledging a start and remembering it re-runs that turn from scratch on relaunch, because the memory that makes a replay a no-op is written after the turn returns. A *graceful* quit is covered, since shutdown reports `execution.interrupted` for every open execution and the control plane refuses to move a terminal execution back.
- **The harness turn has no wall-clock bound**, which is D-034's intent, but the same chaining means a wedged `claude` process holds the lane: every subsequent workspace command from every participant queues behind it indefinitely rather than failing loudly.
- **No approval routing — and the harness does support it.** `needs_approval` exists in the execution and mission state models and is never entered; Claude Code runs under `--permission-mode acceptEdits`, so a permission prompt never reaches a human. This is the largest honesty gap in the harness boundary and blocks any claim about supervised autonomy. A feasibility spike against the installed CLI (**2.1.221**, 2026-08-04) established that it is buildable and how (D-056): with `--input-format stream-json` and `--permission-prompt-tool stdio` the CLI writes a `control_request` carrying `subtype: "can_use_tool"`, the tool name, and its typed input to stdout, and blocks until a `control_response` naming the same `request_id` arrives on stdin; a fixture write was allowed this way and actually happened, with `permission_denials` empty and the session resumable afterwards. The same channel carries `{"subtype":"interrupt","cancel_queued":true}`, which would stop a turn without killing the process or losing the session. An MCP `--permission-prompt-tool` was also proven and is the smaller-blast-radius alternative, but it carries no interrupt. Nothing of this is built.
- **The runner transport is polling.** D-021 chose control-plane WebSockets and D-035 records polling as the shipped transport with identical semantics. Event latency is bounded by the two-second poll.
- **CI results are not ingested.** Novus can run a check a project declared, and re-run one from its own ledger row (D-057); it has no second attributed source of verification, so a row's origin is always Novus and the control can always offer to run it again.
- **Redaction removes values Novus was handed, and detects nothing.** Closed in this slice: the harness transcript is now value-redacted as well as path-masked, and proxy passwords are harvested out of the forwarded variables and folded into the same set (D-052). What remains open is the shape of the protection, not a bug in it. Novus can only remove values it holds, at least eight characters long, in the literal form it holds them — so a credential inside a supplied `.env` *file* rather than supplied as a *value*, one a project prints, one an agent mints mid-turn, an encoded or line-wrapped form of a held value, and a value split across two delivery chunks all survive. Path patterns cover conventional names only; a credential in `notes.txt` is invisible to them, and a template filled in with real values is exempted by name with its contents never read. **Novus does not detect arbitrary secrets and nothing here should be read as claiming it does.**
- **One workstream per mission**, one repository per mission, and no terminal mission lifecycle: a mission cannot be completed or cancelled.
- **Evidence diffs are stored inline** in PostgreSQL rather than in the artifact store D-022 selected, bounded to 150 files and 12 000 characters per file per checkpoint (D-037). A turn touching more files reports the first 150; the commit SHA remains the complete record.
- **Worktrees are never removed** after a mission ends, and there is no cleanup policy for terminal or archived missions.
- The desktop app runs from `pnpm dev` only; there is no packaged, signed, downloadable build, and no Windows or Linux run has happened.
- The light theme is still not proven on rendered screens; every screenshot is dark, macOS, and at three window sizes only.
- Egress default-deny via provider IP rules is proven unworkable (D-024); the egress proxy that replaces it does not exist even as a specification.
- The repository-continuity contract (D-025) is only partly implemented: mission branches, base pinning, and checkpoints exist; remote-update detection, explicit synchronization, conflict presentation, and replacement-workspace reconstruction do not.
