# Progress

## Current milestone

**Two people operating one real mission (D-034 … D-037).** Live today in the desktop app: sign in with GitHub, open a local project, and direct real Claude Code in a dedicated mission worktree under a credentialed local runner. The turn's changes are recorded as git-derived evidence, a follow-up direction resumes the same harness session, and a second authenticated person can join by invitation from another desktop, see the identical durable mission, queue an attributed direction, take the control baton through an explicit request-offer-accept handshake, and have their direction executed by the first person's machine. Closing and reopening either client reconstructs participants, directions, control history, checkpoints, and evidence.

**Terminal and runtime trust (D-043 … D-046)** lands on top of it, proven in the app on 2026-08-03: an interactive terminal on a real PTY that opens in the mission worktree and nowhere else and renders what real programs actually print; a dock that is the terminal alone (D-049), with setup, run, and check output read in the evidence panel's Output section on the machine that produced it (D-050); a setup flow a person reviews, saves, and runs; a declared check invoked on a click whose evidence is bound to the revision it tested; project-stated deadlines with a timed-out outcome that is not a failure; readiness as a declared signal rather than an assumption; secret values supplied at the machine that has them; and a loopback-only preview bridge. The command a participant authorizes is pinned to what they saw, so a turn editing the project's configuration cannot change what their click runs.

**Supervised autonomy (D-062, D-064)** lands on top of both and is proven live on 2026-08-04 against real `claude 2.1.221`: the harness stops before an act it may not take, the question reaches the room, the person holding the baton answers it in the window, and the turn continues — with the permission policy pinned by Novus rather than read from a file the agent can write, and the project's own `CLAUDE.md` handed back explicitly through `--append-system-prompt-file`. Two clients are proven in the app for the same path. Around it, since 2026-08-03: a mission is filed away rather than deleted (D-063), open missions are a window-level working set (D-061), a failed check is run again from its own row (D-057), and the shell was reworked into one top row, a full-height rail, and an evidence panel that is not a menu (D-065 … D-068) — the last of which has visual evidence only up to the 2026-08-05 screenshot set; see the row and [Known gaps](#known-gaps).

**Competing approaches and the decision between them (D-074, D-075, D-079, D-080)** land on top of that, **proven in the app on 2026-08-06**: a second lane forked from the *shared* checkpoint — shown to the person and pinned, never a later revision nobody looked at — with a stated intent, its own branch, worktree, runner credential and baton; lanes that are genuinely operable, as tabs in the room's own strip with a switcher, a per-lane state line, per-lane files, terminal, checks and output, and a composer that names its target and routes every direction to the lane on screen; one surface comparing each lane's own evidence with no score, rank or recommendation anywhere; and a decision that records a person's rationale, the risks they accepted and what was unverified at that moment, followed by a **prepared** pull request nobody has opened.

**Shared sessions inside an approach (D-083)** land on top of all of it, **proven in the app on 2026-08-07**: one lane can now hold several conversations — implement, add tests, review — sharing its branch, worktree, files, checks and baton while each keeps its own transcript and its own harness continuity. A session is created words-first like a mission, titled by its first words; the workspace takes turns, with a sibling session's direction queued visibly and dispatched by the control plane itself when the running turn completes; leaving a session stops nothing; and a reload restores the conversation being read. **On 2026-08-08 the owner redirected the presentation on sight of the built result (D-084)**: a mission's structure — approaches, their sessions, Compare — now nests as a tree under the active mission in the rail, the room's lane and session tabs and both switchers are gone, and a decision is the state line's sentence plus the Compare surface rather than three buttons. The slice's routing audit also found and fixed four places where a request that arrives through a *row* — a stop, a queued direction's resolution, an approval's answer, an enrolment-time dispatch — was resolved against the mission's first lane instead of the row's own.

Cloud execution, Codex, live pull-request tracking, and receipts-as-snapshots remain Not started.

## Status rules

- Every status is one of: **Not started**, **Partial**, **Implemented**, **Blocked**.
- **Implemented** and **Partial** require an Evidence line: a command with observed output, or a link to an artifact a human can inspect. Documentation is never evidence of functionality.
- Evidence comes in tiers, and a claim never borrows a higher one than it has earned:

  | Tier | What it means |
  | --- | --- |
  | **Tested** | A deterministic suite exercises the path. Real processes, real git, real PostgreSQL where the suite says so — but a fake provider or a scripted harness stands in for the outside world. Never live proof. |
  | **Proven in the app** | An Electron end-to-end run drives the real interface in a real window. What a person can actually reach, as opposed to what the modules underneath can do. |
  | **Proven live** | Exercised against the real GitHub or the real Claude Code binary, with the observed result recorded. |
  | **Partial** | Some of the capability is real and some is not, and the line says which. |
  | **Not started** | No implementation. |

- A deterministic suite passing against a fake provider is **Tested**, never "live". A module working is not the same as a person being able to reach it: code that no interface exposes is **Partial** at best, and the line says what is unreachable.
- The Golden V0 workflow ([README.md](README.md#the-golden-v0-workflow)) is the milestone gate for the first implementation: it is not done until two real clients execute all twenty steps.

## Known gaps

- **The live GitHub runtime proof is written but has not been run.** `apps/desktop/e2e/live-github.spec.ts` selects a real repository through the interface, creates a mission, waits for the runner to fetch it, checks the worktree is on the mission branch at the exact recorded base, runs a declared command and a check on it, then independently asserts that no installation token is in `.git/config`, anywhere under the machine's Novus state, in any event payload, or in any recorded check — and that a user session cannot ask for one. It is opt-in and cannot be otherwise: repository access comes from a GitHub App installation bound to a real organization, and that binding is created by a person signing in through their own browser, so the run borrows a profile that is already signed in. Until somebody runs it, "GitHub repositories run locally" stays Partial and the clone path is **Tested**, not proven live.

  ```
  NOVUS_LIVE_GITHUB=1 NOVUS_LIVE_PROFILE="$HOME/Library/Application Support/Novus" \
  NOVUS_LIVE_REPO=owner/name \
  pnpm --filter @novus/desktop exec vitest run --config e2e/vitest.config.ts e2e/live-github.spec.ts
  ```
- **The desktop suite's intermittent failure was a real bug, and is fixed.** It runs files one at a time, and 239 desktop tests passed on a quiet machine while `workspace-clone.test.ts` failed intermittently under load. The gate used to run every step into `/dev/null`, so a failure named the command and nothing else; that was fixed first, and the output then said `fatal: cannot change to '.../worktrees/msn_…': No such file or directory` — a worktree deleted while its creator was still using it. Two callers ask for the same worktree by design (the runner's turn path, and a terminal or file listing the person just opened), and preparation read "is it there" and then deleted what it found, so the loser removed the winner's worktree. The user-visible form is *"This workspace could not be created"*, reported from a real session and read at the time as a GitHub problem. Preparation is now serialised per worktree path (D-058). Proven by seeding the failure — bypassing the serialisation makes the new six-caller test fail with that exact message — and by four consecutive clean runs of a file that had failed one in three.

  Three more failures of the "only under load" family have since been caught **with** their output and fixed, which is the standard this line holds things to. A full `pnpm run e2e` failed the *first* terminal test at its poll ceiling while every later terminal test in the same run passed in under five seconds: the readiness helper decided a shell was ready after ~600 ms of silence, and a cold login shell — this machine's loads conda — emits its startup in bursts whose gaps exceed that window under load, so the keystrokes went into a shell that was not listening. The command is retried now, which addresses swallowed input rather than slowness. The same thing then happened in the *unit* suite, in `workspace-terminal.test.ts`, with the same remedy. The third was not a test problem at all: `workspace-agent.test.ts` failed teardown with `ENOTEMPTY`, because `shutdown()` returned while work queued on a workstream's lane was still running `git` inside the repository — publishing what a project declares reads the repository and can create a worktree. Shutdown now drains those lanes, which also makes quitting the app honest rather than merely quick.

  **The first of the three is not closed.** It recurred on 2026-08-05 in a full `pnpm run e2e` run immediately after a build: the retry ran out of attempts rather than the shell ever answering, and the same spec passed alone on the next run. The retry budget is raised, and that is a mitigation and not an explanation — retrying more often is not the same as knowing why a cold shell under load sometimes never reaches its prompt at all. Nothing has captured that yet, so this stays open.

  **And the family is wider than the terminal.** On 2026-08-05 a full `scripts/gate.sh` run failed three tests in `workspace-agent.test.ts` — a check that never completed inside its 30 s ceiling, and then two `beforeEach` hooks that timed out behind it — while the same file passed alone in 35 s immediately before and the gate passed on the next run with no change in between. So the shape is now known to be: real processes under a loaded machine, first failure cascading into the hooks after it. Still an explanation nobody has, and still open; what is new is that it is not specific to cold shells.
- **A project's `.claude/skills` do not reach the agent**, and that is a deliberate refusal rather than an oversight (D-072). Measured against `claude 2.1.223`: with the settings pinned the session lists 16 skills and none of the project's; with `--setting-sources project` the project's skill appears — and three MCP servers appear with it, alongside the hooks that flag has always re-admitted. `--plugin-dir` is the right *shape* and still refused, because a plugin can carry hooks and MCP servers too; the version that could work is Novus composing a skills-only directory out of the worktree under the containment `CLAUDE.md` already has, which is a slice of its own. What a project can do today is state its conventions in `CLAUDE.md`, which is carried and grants nothing.
- **The harness turn has no wall-clock bound**, which is D-034's intent, but the same chaining means a wedged `claude` process holds the lane: every subsequent workspace command from every participant queues behind it indefinitely rather than failing loudly. **Now visible rather than silent** (D-073): ten minutes with nothing reported carries the *Execution stalled* overlay and the state line says *no progress reported since {time}*, and the recovery is the Stop every non-viewer already holds. Still open: the queue behind it is not shown, and `force_interrupt` remains unimplemented as a distinct verb because Stop already does what it would do.
- **Approval routing pins the permission policy; the project's instructions are handed over explicitly.** `--setting-sources ""` is what stops a `.claude/settings.json` in the worktree deciding what gets asked — and the agent can write that file, so it cannot be an input. It also stopped the repository's `CLAUDE.md` loading, which is now restored with `--append-system-prompt-file` (D-064): measured against the real CLI with tools disabled, a codeword in `CLAUDE.md` is unknown to the model with settings pinned and known once the file is passed. Safe because the two files differ in kind — a settings file grants authority, `CLAUDE.md` grants nothing, and every tool call still reaches the permission router.
- **A controller cannot hand the baton back.** PRODUCT.md's lease model has a `released` state — no recipient, claimable by anyone — and there is no verb that reaches it: control moves by offer, by revocation (which is a force-take, not a release), or by the 30-minute expiry. So a considerate controller who is done cannot say so, and the only path to an unheld lease is silence. The consequences of an unheld lease are now handled and proven (D-073); the way *into* one deliberately is not built, and adding it is a capability-table change rather than an implementation detail.
- **The runner transport is polling.** D-021 chose control-plane WebSockets and D-035 records polling as the shipped transport with identical semantics. Event latency is bounded by the two-second poll.
- **The needs-attention lens now reads every lane of a mission — but names none of them.** Closed on 2026-08-08 for approaches: the mission list's `primaryState` is the mission-level projection PRODUCT.md's state model has always specified — every lane's own state combined with fixed precedence, attention-demanding states, then running, then waiting, creation order within a class so no lane is ranked — and the lens reads it, so a *closed* mission whose background Alternative is waiting on an approval or a direction surfaces in the rail (Tested: `attention.test.ts`, including the regression shape where a sibling's later finished turn used to drown the waiting lane; **not proven in the app** — no end-to-end run drives the lens with a background lane blocked). Still open: the lens row names the mission only, not the lane or the conversation — opening it lands on the lane the tab last read, and the tree's *· needs you* points the rest of the way; and one level down a background **session's** *· needs you* (D-083, D-084) lives only on its tree row and tab, because the lane-level state does say *needs approval* but cannot name which conversation.
- **The harness's own subagents are visible, and not yet a graph.** What exists after D-071: `--forward-subagent-text` is passed, `parent_tool_use_id` is bounded and carried on `harness.text` and `harness.tool` events, and the trace indents a worker's speech and tool steps inside the turn's technical disclosure — grouped under the parent session's turn, never in the speech position, never with a lane, branch, checkpoint, or controller of its own. What a future Approach → Session → main agent → subagents view still has no data for: the spawning tool call's **own id** is not recorded (so a worker's `parentToolUseId` points at an id that appears nowhere else in the log and parent and child cannot be joined after the fact); a subagent has no identity beyond the Task description text; a Task's tool result emits no event, so worker start/finish/failure is unrecorded; `harness.usage` is turn-level, so a worker has no cost of its own; and the renderer uses the parent id only as a boolean, so two concurrent workers' steps interleave in one flat nested list. Recording the tool-use id on `harness.tool` is the smallest next step and touches the closed runner-event union, so it is deliberately a slice of its own.
- **What the pull-request slice still needs**, inventoried read-only on 2026-08-07 against the flow *select approach → review diff and checks → record decision → create draft PR → attach receipt and visual evidence → request review → resolve comments → mark ready → human merges or closes*. Already real: lane selection and branch identity, the diff, the attributed check ledger with staleness, the decision with rationale/risks/unresolved-at-that-moment, and the prepared pull request as a projection with `publishable` honest about local folders. Missing, in dependency order: a `PullRequest` row and lifecycle (no table, no id prefix — *Pull request open* is unreachable); any GitHub PR write (no create call, draft flag, mark-ready, or reviewer request); `pr.manage` and `review.comment` as enforced capabilities (named in PRODUCT.md's table, absent from `CapabilitySchema`); review threading and inline comments; GitHub webhook/poll ingestion for PR state and CI (spec only); the artifact store for visual evidence (D-022, unbuilt) and the receipt as a durable snapshot to attach; a terminal mission lifecycle for "human merged"; and a remote-head guarantee that the decided `checkpoint_sha` is actually what the branch serves before a PR names it.

- **CI results are not ingested.** Novus can run a check a project declared, and re-run one from its own ledger row (D-057); it has no second attributed source of verification, so a row's origin is always Novus and the control can always offer to run it again.
- **Redaction removes values Novus was handed, and detects nothing.** Closed in this slice: the harness transcript is now value-redacted as well as path-masked, and proxy passwords are harvested out of the forwarded variables and folded into the same set (D-052). What remains open is the shape of the protection, not a bug in it. Novus can only remove values it holds, at least eight characters long, in the literal form it holds them — so a credential inside a supplied `.env` *file* rather than supplied as a *value*, one a project prints, one an agent mints mid-turn, an encoded or line-wrapped form of a held value, and a value split across two delivery chunks all survive. Path patterns cover conventional names only; a credential in `notes.txt` is invisible to them, and a template filled in with real values is exempted by name with its contents never read. **Novus does not detect arbitrary secrets and nothing here should be read as claiming it does.**
- **One repository per mission**, and no terminal mission lifecycle: a mission cannot be completed or cancelled.
